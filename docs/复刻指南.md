# codex-micro-waveshare 项目拆解与复刻指南

> 仓库：https://github.com/Douiuiuiz/codex-micro-waveshare
> 定位：**把 Waveshare ESP32-S3-Touch-AMOLED-1.75C 变成"Codex Micro"兼容的无线控制器 + Codex 用量看板（Windows 宿主）**
> 上游：digitsisyph/codex-micro-stopwatch（M5Stack StopWatch C152 + macOS）→ 再上溯 imliubo/codex-micro-4-core2（BLE 兼容层）
> 许可：MIT，第三方非官方项目，与 OpenAI / Work Louder / M5Stack / Waveshare 无关。

---

## 1. 它到底在干什么（一句话）

ChatGPT Desktop 支持一款叫 **Codex Micro** 的 BLE HID 小硬件（一个小圆盘：按键 + 摇杆 + 若干指示灯）。
这个项目的做法是：**用 ESP32-S3 在 BLE 上伪造出同一个 HID 设备（同一个 vendor usage page / report ID / JSON 语义）**，
于是 ChatGPT Desktop 把它当成真 Micro 来对话；同时再挂一条**私有 GATT 通道**，把"Codex 剩余额度 / 重置倒计时"从 PC 端送到手表屏幕上显示。

所以本质上分两层：
- **控制面（必须）**：BLE HID over GATT，双向 JSON-RPC —— 设备发按键/摇杆，主机回 6 个 Agent 的状态灯。
- **数据面（可选）**：私有 GATT service，Windows 上一个 Python 伴进程每 120s 写一次配额。没有它也能用，只是屏幕不显示额度。

## 2. 控制面协议（最核心，复刻必须 1:1 照抄）

### 2.1 HID 描述符

```c
// src/CodexMicroBle.cpp
const uint8_t kReportMap[] = {
  0x06,0x00,0xFF,   // Usage Page 0xFF00 (Vendor Defined)
  0x09,0x01, 0xA1,0x01,
  0x85,0x06,        // Report ID = 6
  0x15,0x00, 0x26,0xFF,0x00,
  0x75,0x08, 0x95,0x3F,   // 63 字节
  0x09,0x01, 0x81,0x02,   // Input  (Data,Var,Abs)
  0x95,0x3F, 0x09,0x02, 0x91,0x02,   // Output (Data,Var,Abs)
  0xC0
};
```
- 走**标准 HID over GATT service 0x1812**（`BLEHIDDevice`），VID `0x303A` / PID `0x8360`。
  Windows 因此把它识别成 HID 设备，ChatGPT Desktop 的 node-hid 集成能直接收 report。
- 设备名 `"Codex Micro"`，厂商 `"Work Louder"`。

### 2.2 分片格式

`sendJson()` 把 `json + '\n'` 按 **61 字节**切片，每片封一个 63 字节 input report：

```
report[0] = 2        // 类型标记
report[1] = chunk_len
report[2..] = 数据
```
每片之间 `delay(4)`，逐片 `input_->notify()`。

### 2.3 设备 → 主机（按键 / 摇杆）

```jsonc
{"method":"v.oai.hid","params":{"k":"ACT10","act":1}}        // act: 1=press 0=release
{"method":"v.oai.hid","params":{"k":"AG03","act":1,"ag":3}}  // Agent 键带 ag 索引
{"method":"v.oai.rad","params":{"a":0.75,"d":1.0}}           // 摇杆: 角度 + 距离
```
键名表（`src/main.cpp`）：

| 键名 | 含义 | 本项目绑定 |
| --- | --- | --- |
| `ACT10` | Mic key（Push to talk） | 按住 BOOT(GPIO0) |
| `ACT09` | Command Key 4（**桌面端出厂默认 = "Continue in a new chat"，新开分支**，详见 §8.25） | PWR 短按 → 发 `ACT09`；想真变成语音聊天须在桌面端改配置 |
| `ACT12` | Send | 点中心表盘 |
| `AG00`..`AG05` | 6 个 Agent 选择 | 屏幕外围 6 个圆 |
| `v.oai.rad` | 模拟摇杆四方向 | 上/右/下/左滑动 |

摇杆角度归一化（`TouchGesture.h`）：右 `0.00` / 下 `0.25` / 左 `0.50` / 上 `0.75`；按下发 `d=1.0`，松手发 `d=0.0`。

### 2.4 主机 → 设备（JSON-RPC 请求，走 output report）

`HostRpcRequest.h` 里分类器：

| method | params | 固件动作 |
| --- | --- | --- |
| `sys.version` | — | 回固件版本 |
| `device.status` | — | 回 `{version, profile_index:0, layer_index:1, battery, is_charging}` |
| `v.oai.thstatus` | **数组** `[{id,c,b,e,s}...]` | 更新 6 个线程灯（颜色/亮度/特效/速度），回 `{"ok":true}` |
| `v.oai.rgbcfg` | 对象 | 回 ok（不实现） |
| `lights.preview` | — | 回 ok |
| `host.focused_app` | — | 回 ok |
| 其他 | — | 回 `-32601 Method not found` |

`v.oai.thstatus` 的 `c` 是 `0xRRGGBB`，`b` 是亮度，`e` 是特效名，`s` 是速度。
**这就是"Agent 状态"的唯一来源** —— 固件没有别的渠道知道 Agent 在干什么。

### 2.5 颜色 → 状态（纯阈值推断，`DashboardUi.h::classify`）

| 判据 | 状态 |
| --- | --- |
| `b <= 0.01` | Unassigned（槽位未分配） |
| `max-min < 48 && max > 150` | Idle（近白） |
| `g > r*1.12 && g > b*1.15` | **Complete**（绿）→ 触发铃声 |
| `b > r*1.12 && b > g*1.05` | Thinking（蓝） |
| `r>150 && g>70 && g > b*1.45` | RequiresInput（琥珀） |
| `r > g*1.2 && r > b*1.2` | Error（红） |
| 其他 | Active |

另外 `effect=="breath"` 或 `s>0.01` 视为"获得焦点"。

### 2.6 Windows 两个大坑（本项目专门处理）

1. **Intel BT 重连不重新订阅 input report 的 CCCD**（esp-idf IDFGH-14581 / PR #15337），notify 被静默丢弃。
   → 固件在 `onConnect()` 里强行把 0x2902 描述符写为 `0x0001`。
2. **默认连接参数下几秒就掉线**。
   → `esp_ble_gap_update_conn_params`：interval 15–30ms、latency 0、supervision timeout 10s。

## 3. 数据面：配额通道

- 私有 GATT：`service 7f0d4e66-2ac2-4a71-bfbe-4ef61a0e5c01`，**可写**特征 `...5c02`（≤512 B）。
- 载荷：`{"remaining_percent": 87, "reset_in_seconds": 12345}`（固件侧 `QuotaPayload.h` 做 0–100 校验）。
- 还有一个历史遗留的 control service `5f9d4e66-...-5c11`，现在固件**不再暴露**，只为兼容旧版 bridge。

### Windows 伴进程 `companion-win/src/codex_watch_all.py`
1. 读 `$CODEX_HOME/auth.json`（默认 `~/.codex`）里的 `tokens.access_token`；
2. `GET https://chatgpt.com/backend-api/wham/usage`，取 `rate_limit.primary_window.{used_percent, reset_after_seconds}`；
3. `remaining = 100 - used`，写成上面那个 JSON；
4. 按广播名 `"Codex Micro"` 扫设备 → 连接 → `write_gatt_char(..., response=False)` → **立刻断开** → `sleep(120)`。

**为什么写完就断**：Windows 同时基本只维持一条 LE 连接，伴进程长期占着会把 HID 链路挤掉，PTT 语音就断了。
**隐私**：只给手表两个数字，token / prompt / 音频一律不出 PC。

（另有 `codex_watch_bridge.py` 订阅 HID 通道驱动 Codex 回合、`codex_watch_companion.py` 走 app-server JSON-RPC 的备选路径。）

## 4. 固件架构（src/ 与 include/）

| 文件 | 职责 | 是否硬件相关 |
| --- | --- | --- |
| `CodexMicroBle.h/.cpp` | BLE HID + JSON-RPC + 配额 GATT + 连接事件队列（FreeRTOS queue / mutex） | **否（可直接复用）** |
| `HostRpcRequest.h` / `QuotaPayload.h` | method 分类 / 配额校验 | 否 |
| `ConnectionHealth.h` | 链路健康：Offline / BleOnly / CodexLive；配额 Fresh / Waiting / Stale | 否 |
| `TouchGesture.h` / `PowerButtonGesture.h` | 滑动分类、电源键单击/双击检测 | 否 |
| `DashboardUi.h` | 466×466 版式渲染（Space Mono vlw 字体） | **是（坐标写死）** |
| `main.cpp` | 状态机 + 触摸/按键/电源/铃声 | 半相关 |
| `Axp2101Power.h` | AXP2101 PMIC 驱动（复用触摸那条 I2C） | 是（但 1.8 板同芯片可复用） |
| `BoardAudio.h` | ES8311 + I2S 引脚 + PA GPIO | 是（1.8 板引脚基本一致） |

### 主循环（8ms 一轮）
```
M5.update() → codex.poll()（消费 output/连接事件/配额三个队列）
→ updatePowerButton() / updateBoardButtons()（BOOT + AXP PEK）
→ M5.Touch.getDetail() → 坐标镜像 → begin/update/finishTouchGesture
→ detectAgentTransitions()（非 Complete → Complete 触发完成铃声 + banner）
→ updatePowerTelemetry()（2s 充电态 / 30s 电量）
→ 脏检查重绘 → updateIdleDimming()（变暗 / desk sleep）
```

### 电源与睡眠策略
- AXP2101 读 SOC / VBUS / 充电状态；`VBUS ≥ 4000mV` 判 Dock（已有 dock 时滞回到 3500mV 防抖）。
- 电池：2 min 变暗（120→24）→ 5 min desk sleep；Dock：10 min / 30 min。
- **desk sleep = 亮度 0 + CO5300 Sleep In**，QSPI 总线与 BLE 都活着（1.75C 没有 IOE1 可断屏电轨）。
- 长按中心 6s（2s 起出提示）→ Travel Mode：AXP2101 `0x10` bit0 软关机，失活则 `esp_restart()` 兜底。
- 完成铃声：软件合成 A4(440) + C#5(554.37) 双音，12 kHz / 270 ms PCM，attack 38ms / release 100ms。

### 触摸的三个坑（1.75C 特有，很有参考价值）
1. CST9217 报的坐标是 **0–232 且镜像** → `screen = (232 - raw) * 2`；不镜像的话点左上角会落到对角。
2. 一次物理点击会发多个 press/release → 提交后 **600ms 同点位（±100px）锁死**，换个点位（另一个 Agent / 中心 Send）立即放行。
3. 放桌上会有鬼影连击 → 2s 内 ≥4 次提交就屏蔽 3s；单次按下 <20ms 不算点击。

## 5. 硬件适配层（这是"移植"真正做的事）

### 5.1 构建
```
platform  = espressif32 @ 6.12.0      # Arduino-ESP32 2.x（不是 3.x！）
board     = esp32s3box
board_build.arduino.memory_type = qio_opi
board_build.partitions = default_16MB.csv
lib_deps  = M5Unified / M5GFX / M5PM1 / M5IOE1 固定 commit 的 zip + ArduinoJson ^6.21.5
extra_scripts = pre:scripts/patch_m5gfx_amoled_sleep.py
                pre:scripts/patch_m5gfx_waveshare.py
```
用 zip 而不是 `git+https`，是为了在没有 git clone 的环境里也能装依赖（内容等价）。

### 5.2 `patch_m5gfx_waveshare.py`（幂等打补丁）
1. 在 M5GFX 的 S3 自动探测**最前面**插入 Waveshare 分支：先在 GPIO14(SCL)/15(SDA) 上探 `0x5A`（CST92xx），命中就手配：
   - QSPI：`CS=12, SCLK=38, IO0-3=4/5/6/7`，`spi_3wire=true`，写 80MHz；
   - 面板：`Panel_StopWatch`，468×468，`offset_x=6`；
   - 触摸：`Touch_CST226`，`SDA=15/SCL=14/RST=2`，**`pin_int = GPIO_NUM_NC`**（这个板上 INT 会让 `getTouchRaw` 直接 bail out，坐标会冻结）；
   - 最后 `board = board_M5StopWatch`。
2. 放宽 `Touch_CST226` 的 chip id 检查：`0xa8`（CST226）之外也接受 `0x92xx`（CST9217）。
3. 放宽 StopWatch 探测：不再强制 `_check_m5pm1() && _check_m5ioe1()`。

### 5.3 `Axp2101Power.h`
**不在 GPIO14/15 上装第二个 I2C master**，而是复用 M5GFX 已经初始化好的 `I2C_NUM_1`，用 `lgfx::i2c::readRegister8/writeRegister8` 访问 AXP2101(0x34)：
`0x00` 状态 / `0x01` 充电 / `0x03` chip id(0x4A) / `0x10` 软关机 / `0x30` ADC 使能 / `0x34` VBAT / `0x38` VBUS / `0xA4` SOC / `0x49` PEK。
SOC 无效时按 3.30–4.15V 线性估电量。

### 5.4 `BoardAudio.h`
ES8311(0x18) 也挂在同一条 I2C 上；I2S 手配 `MCLK=16 / BCLK=9 / WS=45 / DOUT=8`，功放 `PA=GPIO46`。
**必须 `config.internal_spk = false`**：M5Unified 的 C152 profile 会把 I2S WS 放到 GPIO15，那正是触摸的 SDA。

### 5.5 物理按键
- `BOOT = GPIO0`（低有效 + 上拉，40ms 去抖）→ 按住 = PTT。esptool 刷机时也是拉低 GPIO0，不冲突。
- `PWR` 走 AXP2101 PEK：`0x49` 读 `2=短按 / 1=长按`；短按 = 语音聊天切换，长按 = 关机。
- 屏幕左右边缘长按模拟侧键的方案**已废弃**（放桌上左边缘会鬼影，把 Mic 键按住导致 ChatGPT 一直 listening）。

## 6. 复刻到你的 Waveshare ESP32-S3-Touch-AMOLED-1.8：改动清单

> ⚠️ 下面是按公开资料（Waveshare wiki / CNX Software）整理的 1.8 规格，**动手前请老胡按板子丝印和实际 demo 再核一遍**，尤其是屏驱型号和触摸芯片。

| 项目 | 1.75C（本项目） | 1.8（你的板） | 影响 |
| --- | --- | --- | --- |
| 屏幕驱动 | CO5300，466×466 QSPI | **SH8601，368×448** QSPI | **最大工作量**：M5GFX 固定版本里**没有 `Panel_SH8601`**（只有 `Panel_AMOLED` / `Panel_CO5300`） |
| 显示引脚 | CS12 / CLK38 / D0-3=4,5,6,7 | 同（CS12 / CLK11 / D0-3=4,5,6,7） | 需按 1.8 原理图重配（CLK 是 11 不是 38） |
| 触摸 | CST9217 @ 0x5A | **FT3168 @ 0x38**，INT=GPIO21 | M5GFX 有 `Touch_FT5x06`（同族，需验证 chip id/寄存器），或直接自己读 I2C |
| PMIC | AXP2101 @ 0x34 | **AXP2101 @ 0x34**，同一条 I2C(14/15) | ✅ `Axp2101Power.h` 基本可直接用 |
| 音频 | ES8311 @ 0x18，MCK16/BCK9/WS45/DOUT8，PA=46 | 同（另有 MIC DI=10） | ✅ `BoardAudio.h` 基本可直接用 |
| 按键 | BOOT(GPIO0) + PWR(PEK) | 同（BOOT + PWR 两个侧键） | ✅ 可直接用 |
| 马达 | 无 | 无 | haptics 留空操作 |
| 额外外设 | — | XCA9554 扩展 IO(0x20)、QMI8658(0x6B)、PCF85063(0x51)、TF 卡 | 可选；XCA9554 可能管 LCD 复位/PMU INT |
| PSRAM | OPI | 8MB OPI | canvas 仍可放 PSRAM |

**结论：协议层全部可原样搬，真正要重写的只有"板级三件套 + 版式"。**

### 建议的复刻顺序（每步单独验证，别一次性全接）

1. **最小 BLE 固件（不带屏）**
   只留 `CodexMicroBle.*` + 串口打印 RPC。目标：Windows 蓝牙里出现 "Codex Micro"，ChatGPT Desktop 认到它，按键有反应。
   → 这是整个项目**最大的外部风险点**（ChatGPT 版本 / Windows HID 栈），先验证它，别先把屏调完再发现协议不通。
2. **屏幕**：SH8601 驱动。三条路：
   - 给 M5GFX / LovyanGFX 写一个 `Panel_SH8601`（照 `Panel_CO5300.hpp` 抄骨架，填 SH8601 初始化命令序列，可从 Waveshare 官方 Arduino demo 里扒）；
   - 或者干脆换渲染后端（Waveshare 自带 GFX / Arduino_GFX），自己实现 canvas + `pushSprite`；
   - 无论哪条，都要保证后面 `M5Canvas`（sprite + PSRAM + `pushSprite(0,0)`）这套 API 还能用，否则 UI 层要大改。
3. **触摸**：FT3168 → 产出"屏幕坐标系 x/y + pressed/released"。
   建议先写个独立小 demo 打印原始坐标，确认量程（368×448？还是半量程需要 ×2？是否镜像？）——本项目在 1.75C 上就踩了"半量程 + 镜像"的坑。
4. **版式**：`DashboardUi.h` 里 466×466 全部写死，需按 368×448 重排：
   `kWidth/kHeight/kCenterX/kQuotaCenterY/kAgentRadius(56)/kSendRadius(104)/kAgentCenters[6]`。
   注意 368×448 不是正方形，6 个 Agent 的环绕布局要重新算，中心 Send 半径也要相应缩。
5. **电源 / 音频**：AXP2101 + ES8311 基本复用，改 I2S 引脚常量和 PEK 判定。
6. **配额伴进程**：`codex_watch_all.py` 与硬件无关，可原样跑（需 `codex login` 过、装 bleak）。

### 复刻时建议保留的项目习惯
- 板级改动全部加 `CODEX_STOPWATCH_THIRD_PARTY` 注释标记，方便和上游 diff；
- 库依赖用**固定 commit 的 zip**，别用 `git+https`（刷机/构建环境经常没 git）；
- 对第三方库的改动做成**幂等补丁脚本**放进 `scripts/`，别直接改仓库里的库源码；
- 验证分五层单独报：build / flash / pairing / controls / quota，**没在真机上看到的不算验证过**。

## 7. 已知限制（项目自己承认的）

- 无振动马达 → 触觉反馈是空操作；
- AXP2101 只做了电池/VBUS/充电遥测 + PEK 软关机，没做 AMOLED 电轨断电（走线未确认）；
- Intel 蓝牙驱动 < 22.x 容易掉线，建议升到 24.x；
- 一次配对后若控制失效 → Windows 删掉配对重连（CCCD 那一套）；
- ChatGPT Desktop 26.727 只暴露一个 Mic key，所以"语音聊天切换"只能借用 Command Key 4 (`ACT09`)，不是 `ACT11`。
  **⚠️ 2026-09-24 实测修正：`ACT09`（Command Key 4）的出厂默认动作是"新开分支"，不是语音聊天。**
  上游那句注释只是作者的意图，他从没写"要去桌面端改配置"。正解见 §8.25（改桌面端配置，或启用官方
  "Use separate mic keys" 后改用 `ACT11`）。

## 8. 复刻时 M5 遗留代码怎么处理

结论：**要清，而且分两类——"纯死代码直接删"和"功能位必须自己补"。** 但建议先分层、再删，不要边删边改。

### 8.1 纯死代码（1.8 板上永远走不到，直接删）

| 位置 | 内容 | 量级 |
| --- | --- | --- |
| `src/UsbMic.cpp` + `include/UsbMic.h` | USB 麦克风（C152 专属） | **53 KB，最大一块** |
| 所有 `#if defined(CODEX_STOPWATCH_USB_MIC)` 分支 | 含 `stopwatch_usb_mic::`、bootloader RPC、`Preferences` bond 迁移、`esp32-hal-tinyusb` | 遍布 main.cpp / CodexMicroBle.cpp |
| `M5PM1 powerManager` 全部 | `powerManager.begin/setSingleResetDisable/setDoubleOffDisable/timerClear/getWakeSource/shutdown/btnGetState`、`powerManagerReady` 所有守卫分支 | main.cpp 约 60 行 + setup 一整段 |
| `setPanelRail()` / `setPanelReset()` / `M5.getIOExpander(0)` / `kIoeSharedL3bEnable` / `kIoePanelReset` | M5IOE1 电轨与屏复位 | 死代码 |
| `M5.Power.*` 兜底 | `getBatteryLevel / isCharging / getVBUSVoltage / M5pm1.powerOff` | 删（AXP2101 是唯一来源） |
| `M5.BtnA` / `M5.BtnB` / `M5.BtnPWR` | C152 左右实体键 + 红色键兜底 | 删（BOOT/PEK 取代） |
| `PowerButtonGesture.h` + `updatePowerButton()` 的 PM1 路径 | 红色键单击=睡眠/双击=关机 | 删（PEK 短按已改作语音聊天） |

### 8.3 关键决策点：图形后端选谁（决定 M5 能清到什么程度）

- **方案 A（推荐）**：保留 **LovyanGFX/M5GFX 内核**，自己写 `class LGFX : public lgfx::LGFX_Device`，在 `config()` 里绑 `Panel_SH8601` + `Touch_FT5x06`。

### 8.5 清理的收益与代价

**收益**
- 去掉 ~60 KB 死代码（UsbMic 一个文件就 53 KB）；
- `powerManagerReady` / `axpReady` 双分支没了，"电量到底读谁"不再需要推理；
- 板级接口一固定，以后换板只动 `board/`；
- 不再依赖"给第三方库打补丁"这种脆弱做法。

**代价 / 风险**
- 与上游 diff 能力下降 → 建议建一个 `docs/UPSTREAM_DIFF.md`，记录"删了什么、为什么、对应上游哪一段"，以后上游修 bug 能对照着回捞；
- `M5.Speaker` 是现成的 I2S 封装，换成自己写会多花点时间（但你有 ES8311 驱动现成经验）。

### 8.6 另一个必须先验证的风险（跟清理无关，但会决定工作量）

原项目锁 `espressif32 @ 6.12.0` = **Arduino-ESP32 2.x**，并明确写了"stock `BLEHIDDevice` 路径是 2.x 上验证过的配置，手写精简 GATT 表是对 3.x 故障的误判"。

### 8.7 本机实测结论（2026-09-24，step1 固件已编译通过）

上面那条风险已经落地验证，结论和预想的不完全一样：

| 项 | 上游（PlatformIO + 2.x） | 本机（3.3.7-cn） | 处理 |
|---|---|---|---|
| BLE 后端 | Bluedroid | **NimBLE**（`CONFIG_BT_NIMBLE_ENABLED=y`，`CONFIG_BT_BLUEDROID_ENABLED` 未设） | 所有 `esp_ble_gatts_cb_param_t*` 回调改走 `ble_gap_conn_desc*` 分支 |
| conn id | `param->connect.conn_id` | `desc->conn_handle` | 同一套 `ConnectionSet` 逻辑照用 |
| 对端地址 | `param->write.bda` | `desc->peer_ota_addr.val` | 都是 6 字节 |
| `need_rsp` | `param->write.need_rsp` | NimBLE 拿不到 | 配额写入本来就不需要 ATT 响应，传 false |
| CCCD 强写 | Bluedroid 上必须手动写 0x2902 | NimBLE 自动维护订阅 | NimBLE 分支跳过（上层已加 TODO，实测掉线再补 `ble_gap_update_params`） |
| ArduinoJson | 6.x（`StaticJsonDocument<N>`） | **7.4.2**（两类已合并为 `JsonDocument`，旧名只是 deprecated 别名） | 统一改 `JsonDocument` |
| `BLEHIDDevice::pnp()` | 大端写入，需 `swapBytes` 预交换 | **代码没变，仍是大端** | `swapBytes` 照抄，主机才能枚举到 303A:8360 |
| 40-handle 0x1812 | 3.x 上 `createService(uuid, 40)` 注册失败 | NimBLE 动态分配 handle，不生效 | 走标准 `BLEHIDDevice`，**未**启用上游的 `COMPACT_GATT` 手写表 |

→ 也就是说：上游为 3.x 准备的 `CODEX_STOPWATCH_COMPACT_GATT` 手写 GATT 表，在本机（NimBLE）大概率不需要；但**必须看串口的 `BLE HID 0x1812 registered handle=` 是否为非 0 才能确认**，为 0 就回头启用手写表。

### 8.9 根因定位：NimBLE 吃掉了第二个 0x2A4D（output report 消失 → hid_write 恒 87）

这是 8.7 里"3.x 上 `BLEHIDDevice` 不可用"的真正原因，也是 ChatGPT 侧
`WRITE_FAILED (0x00000057)` 的根因。**不是 Windows 缓存，不是长度，不是权限位。**

**症状（很有迷惑性）**：Windows 侧一切正常 —— 配对成功、PnP 里出现
`HID\{00001812-...}_DEV_VID&02303A_PID&8360_...`（"符合 HID 标准的供应商定义设备"）、
报告描述符也被正确解析出 vendor usage page 0xFF00。**但主机每次写 output report 都是
`ERROR_INVALID_PARAMETER (0x57)`**，任何长度都一样。

**根因**：`BLEService::addCharacteristic()` 在 NimBLE 分支下按 UUID 去重 ——

```cpp
#if defined(CONFIG_NIMBLE_ENABLED)
  if (pExisting != nullptr) {
    pExisting->m_removed = 0;      // 命中同 UUID 时，新 characteristic 被直接丢弃
  } else
#endif
  { m_characteristicMap.setByUUID(pCharacteristic, pCharacteristic->getUUID()); }
```

HOGP 的 HID 服务**必须**有多个同 UUID 的 Report characteristic：input / output / feature
全都叫 `0x2A4D`，只靠各自的 `0x2908` Report Reference 描述符区分（`{reportId, 0x01|0x02|0x03}`）。
于是第二个 `0x2A4D`（output）永远进不了 GATT 表 → 报告描述符里声明了 output report，
但 GATT 上没有任何地方可写 → 主机 hid_write 无路可走。`BLEHIDDevice` 内部也是这么建表的，
所以它在 NimBLE 下**必然**不可用，跟"40 handle"没关系。

**判据（唯一可靠的）**：`BLECharacteristic::getHandle()` 在 NimBLE 下**是有效的**
（`pChr_a[i].val_handle = &pCharacteristic->m_handle`，由 `ble_gatts_start()` 填回），
而 `BLEService::getHandle()` 恒为 0xFFFF。所以固件里打印：

```cpp
server_->start();   // 必须在它之后打印：handle 是 ble_gatts_start() 那一刻才分配的
Serial.printf("hid chr handle input=%u output=%u battery=%u\n", ...);
```

- 打补丁前：`input=65535 output=65535`（都不在表里，battery 也是 0xFFFF 因为它同样在
  `server_->start()` 之后才打印，这点容易误判）
- 打补丁后：`input=29 output=33 battery=37` → **output=33 非 0xFFFF = output report 真的进表了**

**修复**：`scripts/patch_nimble_duplicate_char.py`（幂等，带 `--revert`）改本地 core
`libraries/BLE/src/BLEService.cpp`，让 NimBLE 分支**无条件**插入 map。
NimBLE 的 `m_uuidMap` 以 `BLECharacteristic*` 为键（不是 UUID），本来就允许同 UUID 共存，
`getByUUID()` 只是给上层用的便捷访问器，改掉去重不伤别处。

**连带的两条经验**：

1. 改完 GATT 表**必须让 Windows 删掉设备重新配对**，否则它继续用配对时缓存的服务列表
   （bleak 默认读的也是这份缓存，会一直显示旧表）。`use_cached_services=False` 在这台机器上
   直接抛 `WinError -2147418113 灾难性故障`，用不了。
2. 判断 0x1812 有没有注册成功，**不能**用 `bleak` 枚举 —— Windows 会把被 HOGP 驱动独占的
   0x1812 从通用 GATT 客户端视图里隐藏（PnP 里有 HIDClass 节点、bleak 里看不到 1812，
   这两个现象可以同时成立）。只能看固件自报的 characteristic handle。

### 8.11 step2：CO5300 368×448 点亮，与 BLE 协议层共存（2026-09-24）

**结论：第 ② 步一次通过。屏与 BLE 互不干扰，可以进 ③触摸。**

老胡确认的硬件：**CO5300 AMOLED 368×448（QSPI）+ CST820 触摸**。
跟上游 1.75C 的差别不是"换了一块屏"，而是**同一颗 CO5300 的另一种分辨率配置**：
1.75C 是 466×466 / col_offset 0，1.8 是 368×448 / **col_offset 16**。
偏移量、坐标（含圆心/半径）一律不能从 466×466 那套推。

**板级参数（照搬 PocketOracle 在同型板上的实测配置）：**

| 项 | 值 |
|---|---|
| 屏 | CO5300，QSPI 四线，16bpp |
| CS / SCLK | GPIO12 / GPIO11 |
| SDIO0..3 | GPIO4 / 5 / 6 / 7 |
| 分辨率 / 列偏移 | 368×448 / col_offset=16 |
| I2C（触摸 + PMU + IMU + RTC 共用） | SDA=GPIO15, SCL=GPIO14 |
| 触摸 | CST820，走 `Arduino_DriveBus` 的 `Arduino_CST816x`，INT=GPIO21 |
| 图形后端 | **Arduino_GFX**（不是 M5GFX / M5Unified） |

**为什么换图形后端**：上游用 M5GFX + M5Canvas，是受 1.75C 只能靠 M5Unified 板级配置所限。
1.8 板在本机有现成可用的 `GFX_Library_for_Arduino`（自带 `Arduino_CO5300`），
PocketOracle 已用它跑通 → **不需要给 M5GFX 打补丁**（那正是老胡用 Arduino IDE 做不了的
extra_scripts 钩子）。M5Unified / M5GFX 在本项目里一个字节都不用引。

板级层只做组装：`Arduino_ESP32QSPI` + `Arduino_CO5300` + `Arduino_Canvas` 三层，
业务全画在 Canvas 上，`flush()` 时整帧推给面板。

**一个要记住的点：帧缓冲落在 PSRAM。** `Arduino_Canvas::begin()` 用
`aligned_alloc(16, w*h*2)`，368×448×2 = **330KB**；Arduino-ESP32 的 malloc 对 >16KB 的请求
优先走 SPIRAM，不会啃内部 RAM。实测证据：`heap` 从启动到第 26 秒**五次采样完全一致**
（227464）—— 既没挤进内部 RAM，也没泄漏。

**结论**：500ms 一次的全屏 flush（330KB / QSPI）**没有影响 BLE 收发** —— RPC 三部曲照常到达，
`age` 每 5 秒稳定递增，无卡顿丢包迹象。上游担心的"刷屏与协议栈抢 CPU"在这块板上用 500ms
周期还看不出来（等做频谱动画那种高频局部刷新时要再测一遍）。

**状态页**（本步的临时界面，不是最终版式）：标题条 + 板信息 + LINK / BLE / RPC / QUOTA 卡片
+ 6 路线程灯色块（按 ChatGPT 下发的 `rgb` 直接上色，顺带验证 16 位色序）+ heap / redraw。
正式版式按上游 `DashboardUi.h` 重排属于第 ④ 步。

新增串口命令：`t` = 屏自检（红/绿/蓝三帧纯色 + 8 色彩条），用来把"屏没起来"与"颜色/色序不对"
两种故障分开定位。

**下一步（③触摸）**：CST820，用 `Arduino_DriveBus` 的 `Arduino_CST816x`
（`CST816T_DEVICE_ADDRESS`，INT=GPIO21，I2C SDA15 / SCL14）。**先只打原始坐标**，
不做校准，确认量程与镜像方向后再进 ④版式。

### 8.12 step3：CST820 量程与镜像实测钉死（2026-09-24）

**结论：第 ③ 步完成。raw 与屏幕 1:1、无镜像、无缩放 —— 上游那套 `(232-raw)*2` 完全不需要。**

初始化一次成功：

```
[touch] CST820 begin=1 id=0xB7 int=GPIO21 sda=15 scl=14 耗时=22ms
```

`id=0xB7` 正是 CST820 的芯片 ID（驱动读寄存器 0xA7）。
**注意 core 的 board variant `pins_arduino.h` 写的是 SDA=14/SCL=15 且声称触摸是 FT3168
—— 那份 variant 是错的**，以实测的 15/14 为准（ID 读得到就证明总线对）。

**判据怎么来的**：屏幕上画一个 1:1 原始坐标系网格 + 四角彩色标记
（红=左上 / 绿=右上 / 蓝=左下 / 黄=右下），让老胡点对角并**报数值**：

| 点的位置 | 屏幕坐标 | 实测 raw | 若镜像本该报出 |
|---|---|---|---|
| 红块（左上） | (18, 200) | **(1, 200)** | Y 镜像→247；X 镜像→349 |
| 黄块（右下） | (350, 430) | **(353, 447)** | Y 镜像→17 |

两个对角都指向同一结论：**raw = 屏幕像素，量程 0..367 × 0..447，无镜像、无缩放**。

**`irq` 工作正常**：一次点击让 `irq` 从 0 跳到 11 → INT=GPIO21 确实在动，
④ 的触摸可以走中断驱动，不必只靠 100ms 兜底轮询。

**两条方法上的教训（比结论更值得记）：**

1. **判定"有没有镜像"必须让用户点两个对角并报数值**，而不是"看十字画在哪"。
   单点会因手指偏移产生歧义 —— 红块中心 x=18、实测报 1，光看这一个数分不清
   "点偏了"和"轴反了"。数值与预期值比对才是无歧义判据。
2. **给"需要人操作"的采集窗口必须留足时间（≥5 分钟）**。首轮把窗口开成 45 秒，
   老胡读到消息时窗口已关，拿到的是 `irq=0 smp=0` 的假故障。

**诊断通道（值得固化到任何 I2C 触摸项目）**：驱动的 `IIC_Read_Device_Value()` 只认
`{0,1,2}` 三个返回值，其它一律折成 −1，于是"真的没人点"和"点了但驱动认不出"在串口上
长得一模一样。破法 = **绕过驱动解码、直读原始寄存器**（`BoardTouch::readRegs()`，
一次事务读 0x01..0x06），并加串口命令 `d` 转储、`rd/wr <reg>` 读写单寄存器。
本案靠它拿到寄存器级旁证：触摸时 `03=40 04=01` → x=(0x40&0x0F)<<8|0x01=1，
`05=00 06=C8` → y=200，与驱动解码一致。

### 8.13 step4：看板版式从 466×466 重排到 368×448（2026-09-24）

上游 `DashboardUi.h` 的坐标是**整块硬编码**给 466×466 的，本板 368×448 **不是正方形**，
所以不是"整体缩放"，而是三条各自独立的约束：

**① 六键环不能再用正圆 → 改椭圆轨道。**
上游环半径 164（正圆）。本板水平半宽 184 < 垂直半高 224，正圆会让左右两键顶到屏幕边缘。
改椭圆 `kOrbitX=111 / kOrbitY=168`。

**② "键不撞表盘"的判据是 `中心↔键心距离 > 表盘外径 + 键半径`。**

| | 上游 466 | 本板 368×448 |
|---|---|---|
| 表盘外径 / 内径 | 104 / 94 | 95 / 86 |
| 键半径 | 56 | 40 |
| 中心↔键心距离 | 164 | 139 |
| 判据余量 | 164−160 = 4 | 139−135 = 4 |

**③ 字体不能照抄。** 上游用 SpaceMono **VLW** 字体（TFT_eSPI / M5GFX 专有格式），
Arduino_GFX 没有对应实现。改用 GFX 内置点阵 + `setTextSize`，
**每行字号按"表盘内圆在该行的可用宽度"反推** —— 例如 `linkHealth` 那行 y=166 处
内圆半宽 = √(86²−58²) ≈ 63.5（可用宽度 127px），所以 "CODEX LIVE" 用 size 2（120px）刚好。

**最终几何**：

```
中心 (184, 224)   六键半径 40   表盘外 95 / 内 86   Send 命中半径 95
A1 (184, 56)   A2 (295, 140)  A3 (295, 308)
A4 (184, 392)  A5 (73, 308)   A6 (73, 140)
```

**Arduino_GFX 与 M5GFX 的 API 对应**（这几条决定改造成本）：

| 上游（M5GFX） | 本板（Arduino_GFX） | 说明 |
|---|---|---|
| `fillSmoothCircle` | `fillCircle` | 抗锯齿版没有；AMOLED 上硬边圆反而更利 |
| `fillSmoothRoundRect` | `fillRoundRect` | 同上 |
| `fillArc(x,y,r1,r2,start,end,c)` | **同名同签名** | 角度基准实测一致 |
| `setTextDatum(middle_center)` | **没有** | 自己按 `strlen*6*size` 算宽度居中 |
| SpaceMono VLW | GFX 内置点阵 / u8g2 桥接 | `setFont(const uint8_t*)` 可挂 u8g2 字体 |

**`fillArc` 的角度基准值得单独记**：读 `Arduino_GFX.cpp::writeFillArcHelper` 确认
扫描从 `xs=-oradius` 起、`start<90` 时 `xs=0` → **0° 在 12 点、顺时针**，与 M5GFX 一致
→ **上游的进度环那一段可以原样照搬，不做任何补偿**。

**触摸交互照搬上游 `main.cpp` 的三段式状态机**：

```
begin : 命中 Agent 键 -> 候选(待提交) ；命中表盘 -> 候选(待提交 Send)
update: 位移超阈值 -> 改判滑动，取消按键候选，发 sendJoystick(angle, 1.0)
finish: 抬起；候选存活够久才提交 —— 按键发 AGxx/ACT12 的 1→0 脉冲
```

- 幻触抑制照搬上游思路：提交后进锁定期，锁定期内**落在同一位置**的按下当残留吞掉，
  **落到别处**算新操作放行。
- 上游的 `kSwipeThresholdPx=100` 是为 1.75C（466 屏 / 表盘半径 104）抬上去的，
  本屏按比例取 **80**。
- 按键映射原样照抄：`AG00..AG05` = A1..A6、`ACT12` = 表盘 Send、`ACT09` = 语音聊天、
  `ACT10` = 左麦克风（BOOT 长按）。滑动归一化角度 **右 0.00 / 下 0.25 / 左 0.50 / 上 0.75**。
- 命中测试与绘制**共用同一份 `kAgentCenters`**，不做坐标变换层 —— 这正是 8.12 结论
  （raw = 屏幕像素）带来的最大便利。

### 8.14 step4 的观测性补丁，与 CST820 的寄存器残留（2026-09-24）

这一轮查出三件"不影响功能、但会让下一次排查变成猜谜"的事，值得单独记：

**① 成功路径也要出声。** 写 step4 时我把 `if (!display.begin()) ...` 写成只在**失败**时打印，
成功静默。结果"屏/触摸起来了没有"只能靠 status 行的 `canvas=1 tp=1` 反推 ——
而 `tp=1` **无法区分**"CST820 被认出来"和"恰好 `begin()` 没报错"。
**判据要带上身份与参数**，不能只给一个 `ok=1`：

```
[screen] CO5300 就绪 368x448 canvas=1 耗时=384ms
[touch] CST820 ready id=0xB7 int=GPIO21 sda=15 scl=14 addr=0x15 耗时=22ms
```

`id=0xB7` 才是芯片身份的硬证据（驱动读 0xA7）。

**② 驱动值标签别猜，去读枚举。** `Arduino_IIC_Chip.h` 里 `Value_Information` 的顺序是
`TOUCH_FINGER_NUMBER(0) / TOUCH_COORDINATE_X(1) / TOUCH_COORDINATE_Y(2)`，
所以 `driverValue(0/1/2)` 是 **finger / x / y**，原来标成了 `x / y / f`。
实测 `driver finger=0 x=356 y=445` 与直读寄存器解出的 (356,445) **逐位一致**
→ 驱动解码本身没问题；8.12 说的"驱动不可信"只针对它把 FingerNum > 2 的值折成 −1 那一处。

**③ CST820 的坐标寄存器跨 MCU 复位保留。** 复位后立刻 `d`：

```
[tdump] 01=00 02=00 03=41 04=64 05=01 06=BD
  01 GestureID=0  02 FingerNum=0  03/04 X=356  05/06 Y=445
```

FingerNum=0 表示**没人碰**，但 XY 仍然是 (356,445) —— 正是上一次会话最后那次触摸的位置
（8.12 里点黄块的 353,447）。也就是说：

> **任何"开机直接读 XY 当初始位置"的写法都会凭空得到一个幻触。**
> 必须先判 `FingerNum`，再读 XY。

本项目的 `BoardTouch::poll()` 本来就是先读 FingerNum，所以没踩到；但上游 1.75C 那三个触摸坑
（见 4.4 节）里就有这一类，逻辑是相通的。

**④ 新增 `u` 命令**：把"屏幕此刻应该长什么样"打成文本，用来和肉眼看到的实物逐项核对 ——
版式是算出来的，只有"文字描述 = 实物"才能证明没算错：

```
[ui] 368x448 center=184,224 orbit=111,168 keyR=40 dial=95/86 sendR=95
[ui] link=CODEX LIVE dial=LEFT quota=no reset=NO QUOTA DATA batt=100% charging=0
[ui] A1 (184, 56) status=idle src=#FFFFFF fill=#B619 b=1.00      ← 六键同此
```

`tools/tap_touch.py` 的收尾命令已改为 `d` + `u` + `s`，每次采集自动带一份 UI 快照。

### 8.15 900 秒采集零触摸 → 根因是 CST820 的自动休眠没关（2026-09-24）

**现象。** step4 烧好后开了两次采集窗（600s 和 900s），整窗状态行都是：

```
[status] ... tp=1 irq=0 smp=0 raw=(0,0) down=0 ui=0,0 swipe=-1 commits=0
```

而同一时间 BLE 是好的（`connected=1 rpc=1`，主机每 60s 发一次 `device.status`），
板子从 0.25s 跑到 910s 没重启过。收尾 `d` 读回来 `01=00 02=00`（FingerNum=0），
`gpio21=1`（INT 空闲）。也就是说**芯片全程答"没有手指"**。

**这一类现象必须先分清两件事**，否则全靠猜：

| | irq | smp | 含义 |
|---|---|---|---|
| 没人碰 | 0 | 0 | 芯片活着，只是没事件 |
| 轮询根本没跑 | 0 | 0 | 代码路径断了 |
| 芯片报了但驱动不认 | 0 | 0 | 值被折成 −1 |

三种情况在只有 `irq` / `smp` 两个计数时**长得完全一样**。所以加了第三个计数
`pol`（真正走了 I2C 的轮询次数）—— `pol` 在涨而 `smp` 不动，才是"确实问了 N 次、
每次都说没有手指"。900s 那次没有这个计数，所以无法当场排掉后两种，只能回头查代码。

**根因（读驱动源码得到）。** `Arduino_CST816x.h` 里的初始化数组只有一项：

```c
static const uint8_t CST816x_Initialization_BufferOperations[] = {
    BO_BEGIN_TRANSMISSION,
    BO_WRITE_C8_D8, CST816x_WR_DEVICE_INTERRUPT_MODE, 0B00010000,  // 0xFA
    BO_END_TRANSMISSION,
    BO_DELAY, 20};
```

**它只写 0xFA（中断模式），从来没有碰 0xFE。** 而 0xFE = `DisAutoSleep`，
**出厂默认 0 = 允许自动休眠**，超时 2 秒没触摸就进低功耗 Standby。三个独立来源都这么写：

- `albsod/pinetime-hypnos` 寄存器表：`REG_DIS_AUTO_SLEEP 0xFE`，`Default 0 = enable auto sleep. Any other means disable`
- 汇顶 CST816S 寄存器说明 PDF（0xFE 一节）：`默认为 0，使能自动进入低功耗模式；为非 0 值时，禁止自动进入低功耗模式`
- `fbiego/CST816S` + Waveshare 文档：这个状态就叫 **Standby**，关掉之后芯片留在 **Dynamic** 模式，
  响应变好、代价约 **1.6 mA**

`SensorLib` 里 `TouchDrvCST816::disableAutoSleep()` 对 `CST820_CHIP_ID` 做的也正是
`writeRegister(CST8xx_REG_DIS_AUTOSLEEP, 0x01)`。

**为什么 step3 当时是好的。** 进入 Standby 后能不能被触摸唤醒，取决于低功耗扫描参数
（`LpScanTH` 默认 48 / `LpScanWin` / `LpScanFreq`，全是出厂值）。step3 那次是复位后
紧接着连续点四处角，全都落在 2 秒活跃窗内、且手一直在动，所以量程能测出来；
step4 那两次窗口，之前都有长于 2 秒的空档，芯片早就睡了，于是**整块屏再无任何响应**。

> 这不只是测试环境的坑：**产品形态就是"偶尔去点一下"**，自动休眠开着意味着
> 空闲后的第一下必然被吞。这是真 bug，不是采集脚本的问题。

**修法（`firmware/step4_dashboard/BoardTouch.{h,cpp}`）。**

```cpp
// begin() 里，chip_->begin() 成功之后：
setAutoSleep(false);          // 写 0xFE = 0x01，关掉自动休眠

bool BoardTouch::setAutoSleep(bool enable) {
  const uint8_t value = enable ? 0x00 : 0x01;   // 0=允许休眠，非0=禁止
  if (!writeReg(kAutoSleepReg, value)) return false;
  delay(5);
  // 自保护：个别批次 CST816x 在关掉休眠后寄存器会整体读成 0xFF、触摸直接死
  //（SensorLib 专门为 CST816T 加了这条判断）。用 FingerNum 当探针，
  // 一旦命中就把 0xFE 写回 0 回滚 —— 这个动作要么生效、要么原样退回。
  uint8_t regs[6] = {};
  if (readRegs(0x01, regs, sizeof(regs)) && regs[1] == 0xFF) {
    writeReg(kAutoSleepReg, 0x00);
    autoSleepDisabled_ = false;
    return false;
  }
  ...
}
```

配套的现场手段：

- 串口 `a` 查询 / `a0` 关闭 / `a1` 恢复 —— 一次烧录就能对比两种模式的响应
- status 行加 `pol=`（轮询次数）和 `as=`（休眠是否已关）
- `d` 命令加读 `0xFE` 本身
- 开机打印 `[touch] autoSleep reg0xFE=1 disabled=1`，这是"到底写进去没有"的硬证据

**遗留取舍。** 关休眠多花约 1.6 mA。第 ⑤ 步做 AXP2101 电池管理时要重新决定：
要么保持关休眠，要么改成把 `LpScan*` 参数调灵敏后放回自动休眠。

> **⚠️ 本节结论已被推翻，见 8.16。** 自动休眠确实是个真隐患（值得永久修掉），
> **但它不是那两次零触摸的原因** —— 真正的原因是那两次窗口里屏根本没人碰。
> 反证很硬：step3 那次是窗口第 268 秒才点中黄块的，如果"2 秒休眠叫不醒"成立，
> 268 秒那一下不该成功。

### 8.16 step4 触摸交互打通，以及两个"按比例缩放常量"造成的真 bug（2026-09-24）

**结论先给。** 第三次采集窗（300s）里老胡点屏，**触摸完全打通**，六键 / 表盘 /
滑动三条交互路径全部在串口上留下事件，HID 报文也真的发给主机了：

| 时间 | 串口 | 对应 HID |
|---|---|---|
| 24.16 → 24.44 | `begin x=184 y=38 agent=0` → `agent A1 -> AG00 pulse (1 commits)` | `HID key=AG00 action=1/0` |
| 26.72 → 27.42 | `swipe DOWN angle=0.25 press` → `release`（共 3 次） | `HID joystick angle=0.25 distance=1.00/0.00` |
| 29.90 / 30.49 / 30.75 | `send -> ACT12 pulse (2/3/4 commits)` | `HID key=ACT12 action=1/0` |
| 32.03 | `agent A2 -> AG01 pulse (5 commits)` | `HID key=AG01` |
| 32.77 / 33.03 | `agent A3 -> AG02 pulse (6/7 commits)` | `HID key=AG02` |
| 33.78 | `agent A4 -> AG03 pulse (8 commits)` | `HID key=AG03` |

窗口一检到触摸就提前收尾（32.22s 结束），`irq=304 smp=246 pol=507`。

**8.15 的更正。** 自动休眠不是那两次零触摸的原因。真正的解释就是最简单的那个：
**那两次窗口里没有人碰屏。** 判据链：
`q` 电学自检（把 GPIO21 直接拉低 5ms → **不经过触摸芯片**）让 ISR 立刻 +1，
证明"GPIO21 + attachInterrupt + ISR"这条链子完好；`pol` 涨到 3502（≈9.7Hz）而
`smp` 恒 0、`0xFE=1 disabled=1`、`0xFA=40` 回读正常 —— 芯片被实打实问了 3500 次、
每次都答"没有手指"。至此"没人碰"成为唯一自洽的解释。

关休眠的补丁**保留**（空闲后第一下被吞确实是产品级隐患），但它不是根因。

**真 bug 一：按屏幕尺寸等比缩放上游常量。** 我原来把上游的数字按 `368/466`
折算了一遍，理由写得挺像回事（"表盘半径 95，按比例折 ≈91，取 80"）。
**这个推理是错的 —— 抖动是数字化仪的电气特性，跟屏上有多少像素无关。**

上游那段注释其实就是答案（`src/main.cpp:34-39`）：

```cpp
// CODEX_STOPWATCH_THIRD_PARTY: raised from upstream's 52 to 100. On the
// Waveshare 1.75C the touch digitizer jitters enough that a tap on the large
// center Send dial (radius 104) often drifts past 52px, which the swipe
// classifier stole as a joystick gesture and cancelled the Send.
constexpr int kSwipeThresholdPx = 100;
```

也就是说：**"点表盘被偷成滑动、Send 被取消"在这个项目里早就是已知问题**，
上游的解法是把阈值从 52 抬到 100。而我把它压到了 80 —— 比他们踩坑前的值还低 20%。
实测现象完全吻合：窗口里 4 次点表盘，**前 3 次被判成 `swipe DOWN`**，只有第 4 次
真正发出了 Send。

**一次点按提交两次。** `kPhantomSameSpotPx` 我取 30，上游是 **100**。
CST820 一次物理点按会报好几轮 press/release，靠"落点是否在上一次提交点附近"

> **教训（可复用到任何移植）。** 上游代码里那些"
> 为了适配某块板子而调过的"常量，**携带着原作者踩坑的信息，不能当自由参数按比例缩放**。
> 正确做法是先读它的注释、理解它为什么是那个数，再决定要不要动。
> 判断依据：如果这个数描述的是**物理量**（长度、时间），可以按尺寸折算；
> 如果描述的是**噪声/抖动容限**，它是电气特性，跟屏幕大小无关，一处一块板子单独实测。

**真 bug 二之外，还加了一条上游没有的结构性护栏。** 抬高阈值只是把"点按被偷"
的概率降低；`insideStartCandidate()` 让它**结构上不可能**：

```cpp
// 手势当前点是否还落在"按下时命中的那个区域"内
bool insideStartCandidate(int16_t x, int16_t y) {
  if (agentPressed && activeAgent >= 0)
    return dashboard::agentAtPoint(x, y) == activeAgent;
  if (sendPressed) return dashboard::sendAtPoint(x, y);
  return false;
}

// updateGesture 里，距离阈值之后再加一道：
if (insideStartCandidate(x, y)) return;   // 还在起始区内 -> 继续当按键候选
```

理由：从表盘出发的**真滑动必然离开**半径 95 的圆（阈值就是 100），而被偷走的
点按不会。已知代价：从表盘边缘朝圆心拖 100px 会停在圆内、仍算点按 ——
但"从表盘往里划"本来就不是有意义的手势，可接受。

```cpp
}

```

**命中圈 44px 不是随手写的，它正好让键和表盘相切。** 侧键（A2/A3/A5/A6）到圆心距离

`beginGesture()` 里命中判定是"先查键、后查表盘"，所以只要键的命中圈不侵进表盘，
就永远不会出现"点键变成点表盘"。**反过来说：这个值不能随手加大。**

**新发现（本轮最重要）：INT 一次点按只来约 1.3 个下降沿，坐标流其实是兜底轮询在撑。**

```
irq 增长：t=15.2s 是 1 → t=40.25s 是 38 → t=45.25s 是 58   （6 次手势期间总共就这些）
pol 增长：稳定 ~10.8 次/秒                                  （= 100ms 兜底周期的满速）
smp 总数：10                                                （6 次手势只采到 10 个点）
```

去驱动里核对过：`TOUCH_DEVICE_INTERRUPT_PERIODIC` 写的是 `0xFA = 0b01000000`（bit6 EnTouch），
驱动自己的注释就是"**检测到触摸时，发出低脉冲**"——**一次触摸一个脉冲，不是按住期间连续脉冲**。
换句话说 `PERIODIC` 这个名字有误导性，它并不提供坐标流；而 `Peripherals` 的 bit7 EnTest
在本芯片上还写不进去（见 8.16）。**结论：本板的坐标流只能靠轮询。**

于是 `kPollFallbackMs = 100`（10Hz）就成了滑动手势的瓶颈：一次 200ms 的点按只采到 2 个点，
一次 500ms 的拖拽也只有 5 个点。**已改**：手指按住期间改用 `kPollActiveMs = 20`（50Hz），
代价只是"手贴在屏上时"每次 loop 多读 3 个 I2C 寄存器。

```cpp
// BoardTouch::poll()
const uint32_t interval = pressed_ ? kPollActiveMs : kPollFallbackMs;
if (!irq && (now - lastPollMs_) < interval) return;
```

采集脚本的提前收尾已从 30s 放宽到 **90s** —— 做一次合格的长拖拽（>100px、按住 0.5s）
比连点六个键更费时间，30s 不够。

**顺带确认了一个"差点误判"的边界**：这轮有一次尝试落在 `(41,109)`，距 A6 中心 `(73,140)`
= 44.5px，**只差 0.5px 落在 44 的命中圈外**，被判 `agent=-1`。所以 A6 不是"点不到"，

### 8.19 触摸坐标的系统性偏差：数字仪增益比屏大 14%/20%（2026-09-24）

**现象。** 老胡报"`v1` 的十字跟着手走，但有偏移" —— 这一句把问题从"命中半径不够"
改判成"芯片坐标与屏幕坐标之间存在系统性偏差"。**注意这句话只有开着 `v1` 才能说出来**：
没有屏上十字，用户能表达的只有"有时候点不到"，根本分不清是手指偏了还是坐标偏了。

**判据一：偏差有方向规律。** 六键各点一次（第一轮）：

```
A1 (184, 56) → raw (188, 18)  偏 (+4,-38)     A4 (184,392) → raw (178,414) 偏 (-6,+22)
A2 (295,140) → raw (314,144)  偏 (+19, +4)    A5 ( 73,308) → raw ( 44,301) 偏 (-29, -7)
A3 (295,308) → raw (324,336)  偏 (+29,+28)    A6 ( 73,140) → raw ( 48,114) 偏 (-25,-26)
```

**四个方向全部"往外偏"**（上更上、下更下、右更右、左更左），而**屏心几乎不偏**。
这不是平移，是 **`raw = k*(screen - center) + center` 且 `k > 1`** 的形状 ——
**触摸数字仪的坐标增益比屏大**。

**判据二：不是手抖。** 同一键两次独立取点的差：A6 只差 1px、A3 差 9px、A4 差 16px。
系统性误差才会这样复现；手抖应该四处乱散。

**第一版校准器是错的（很重要）。** 我用 **6 参数完整仿射**（含旋转/剪切）+ 每键只点 1 次：
6 个点解 6 个未知数，而单点噪声有 ±30px → 纯粹过拟合，
**`rms=59.95px`，比完全不校准还差**（头两次失手 143px / 209px 直接把解带飞）。

> **参数个数必须匹配我们对物理模型的先验，不是越多越好。**
> 既然数据指向"每轴一个增益 + 一个截距"，就用 4 参数；多出来的自由度数只会去拟合噪声。

**第二版（定稿）：4 参数 + 每键 3 次取中位。**

- 模型：`raw_x = calKx*sx + calCx`，`raw_y = calKy*sy + calCy`（无旋转、无剪切，可逆）；
- 每键连点 3 次取**中位数**（抗单次失手，同时打印 `max-min` 当重复性指标）；
- 合理性检查：增益不在 `0.6~1.6` 就**整份丢弃**，绝不把垃圾常量灌进坐标换算。

18 点实测结果：

```
[cal] A1 中位 raw=(184, 31) 偏=( +0,-25)  重复性 max-min=( 8, 3)
[cal] A2 中位 raw=(324,124) 偏=(+29,-16)  重复性 max-min=( 7, 9)
[cal] A3 中位 raw=(315,338) 偏=(+20,+30)  重复性 max-min=( 9,12)
[cal] A4 中位 raw=(195,419) 偏=(+11,+27)  重复性 max-min=(17,12)
[cal] A5 中位 raw=( 69,331) 偏=( -4,+23)  重复性 max-min=(13,12)
[cal] A6 中位 raw=( 65,114) 偏=( -8,-26)  重复性 max-min=( 8,12)
[cal] 六个键的中位偏差均值 = (+8.0, +2.2) px
[cal] model  raw_x = 1.1374*sx - 17.3   raw_y = 1.1974*sy - 42.1
[cal] 数字仪增益 = 1.137 (x) / 1.197 (y)  ← 1.000 = 与屏完全一致
[cal] 拟合残差 rms=7.84px worst=9.82px  每点: 8.6 5.2 9.8 7.4 4.6 9.7
```

- **残差 7.84px**，比第一版降了 7.6 倍，比修前的 24~40px 偏差降了 3~5 倍。
- **逐键重复性只有 8~17px** ⇒ 单次落点的手抖约 ±10px，这是**误差地板**：
  7.84px 已经贴着噪声极限，再增加参数只会过拟合。
- **两个轴的增益不同**（1.137 vs 1.197）⇒ 更像"触摸面板物理尺寸 ≠ 显示区尺寸"，
  而不是纯粹的分辨率配置写错。**换屏/换板必须重新校准**，这几个数不能跨板套用。

**持久化与现场手段。**

- **出厂默认常量**（`kCalDefKx/kCalDefCx/kCalDefKy/kCalDefCy`）直接作变量初值，
  且 `calFitOk = calApplied = true` ⇒ **开机即应用**，不必每次上电手工 `z1`。
- **NVS**（`Preferences`，命名空间 `touchcal`）：`c` 校准成功后 `saveCalToNvs()`，
  开机 `loadCalFromNvs()` 优先读数，没有才用出厂默认 ⇒ **校准一次，掉电不丢**。
- 串口命令：`c` 校准 / `z1` 应用 / `z0` 关闭 / **`z2` 丢弃 NVS 回到出厂默认**；
  `z0`/`z1` 会顺带打印"当前常量 + 来源（NVS / 出厂默认）"，排查"越校越歪"时最关键。
- `v1` 的十字颜色就是修正开关的状态：**黄 = 未修正 / 青 = 已修正** ——
  "修没修对"在同一窗口里肉眼直接可比，不需要靠串口数字想象。

**⭐ 一个只在"变换默认打开"时才暴露的 bug（可复用教训）。**

`beginGesture()` 收到的是 `pollTouch()` 里**已经过修正**的屏幕坐标，而校准分支
直接把 `x,y` 存进 `calPts[].rx/ry` 当"raw"用。

- 修正关闭时恰好不出错（那时 `sx == sample.x`），所以一直没暴露；
- **一旦出厂默认值让开机就 `calApplied=true`，第一次 `c` 就会踩到**：
  存进去的是"已经除过 1.1374"的值，再拟合一次得到的增益约 `1/1.1374 ≈ 0.879`，
  **越校越歪**。

修法：`beginGesture(x, y, rawX, rawY)` 多收两个原始坐标，校准分支**只存 raw**；
同时 `c` 里**不再清 `calApplied`/`calFitOk`**（校准取 raw 与当前是否应用无关，
保留旧修正可以保证"校准中途放弃"也停在上一套可用值上，而不是莫名掉回未修正状态）。

> **教训：标定/校准的输入必须是"未加工"的原始量。**
> 只要系统里存在一层可开关的变换，就要保证标定路径**永远走在变换之前**，
> 否则"标定 + 变换"会互相污染 —— 而且**只在变换默认打开时才暴露**，
> 极易被"关闭时测试通过"骗过去。

**工具侧配套。** `tools/tap_touch.py` 加了第 4 个参数 `mode`：
`verify`（默认）只发 `v1` + `z1` 直接验证已有修正；`cal` 才发 `c` 重新校准。
**默认行为从"开窗即重校准"改成"开窗即验证"** —— 校准是要人肉点 18 下的重活，
不该在每次验证时都来一遍。另外 `c` 模式**不能先发 `z0`**：校准取的是 raw 坐标，
与是否应用修正无关，而先 `z0` 反而会让十字回到黄色原始位置，看不出点得准不准。

不是坐标误差**。命中半径 44px 对这个噪声地平有 2 倍以上裕度，够用。

```
[touch] agent A1..A6 -> AG00..AG05 pulse   （commits 1..6，一轮全中）
[touch] send -> ACT12 pulse (7 commits)    （点表盘）
[touch] swipe RIGHT angle=0.00 press / release
[touch] swipe DOWN  angle=0.25 press / release
```

**依然为 0 的：`noise burst -> suppress`。** 上一轮改的"同区域计数"生效了：
这轮 15 次提交里一个 `[touch] noise burst` 都没出现，两次被吞以前必触发的连续快点
（A1→A1→A1、六键快速连点）都正常提交。

**新抓到并修掉的一个真 bug：幻触判据写成了逐轴比较（Chebyshev）。**
`abs(x-lastX)<=100 && abs(y-lastY)<=100` 等价于一个 200×200 的方框，
但**目标之间的真实几何是圆**。实测证据：

```
[170.18] agent A6 -> AG05 pulse     ← 提交在 (66,130)
[170.61] locked out x=164 y=224     ← 紧接着点表盘，被吞
```
逐轴差 `98 / 94` 都 <100 → 判成"同一位置"；**欧氏距离其实是 136px**，是另一个目标。
而所有真幻触的欧氏距离都 <40px。⇒ 改成**欧氏距离判据**即可干净分开两类，
**不需要动 100px 这个上游实测常量**（动常量会引入新的取舍，换判据不会）。

> **教训：凡是"距离/半径"语义的判据，就用欧氏距离，别图省事写成逐轴比较。**
> 逐轴比较把圆形邻域撑成方形，斜角方向的有效半径会膨胀到 `√2 × r`
> —— 在 368×448 上，这多出来的 41px 刚好大到能吞掉隔壁目标的点按。

`locked out` 现在会打印实测距离 `d=`，下次判断"是不是又被误吞"不用再手算。

**收尾快照**（窗口末）：`heap=225192` 全程零抖动，`smp=513`、`irq=819`、`pol=2897`
（轮询持续在跑），`raw` 与 `ui` 都停在最后一次抬手位置 —— 无泄漏、无卡死。

**④ DashboardUi 至此收尾。** 剩余待做：⑤ AXP2101 电源（电量目前是写死的 100）+ ES8311 音频；

### 8.21 step5：AXP2101 电源遥测 + ES8311 完成提示音（2026-09-24）

#### 为什么这两块新东西不需要问用户就能自证

上一轮问过老胡"电池插了没 / 喇叭接了没 / PWR 键要不要做"，没有回话。
所以这一轮**改成不问**：把读数打出来，让板子自己说。
开机/敲 `p` 会打三行，这三行同时回答了三个问题：

| 日志 | 回答了 |
|---|---|
| `[pmu] AXP2101 probe=0 id=0x4A(对) ADC 0x30=0->5 电池检测 0x68=0->1 INTEN2 0x0->0xF` | PMU 在不在总线上、身份对不对、三处使能写没写进去 |
| `[pmu] 首次读数 电量=..% 充电=.. VBUS=.. vbat=..mV vbus=..mV` | **到底有没有接电池**（`vbat` 只有几百 mV 或 `电池在位=0` 就是没接） |
| `[audio] ES8311 addr=0x18 ack=.. codec=.. i2s=..` | 编解码器认不认、I2S 起没起来 |

**通则：能靠"设备自己打出来的现场"回答的问题，不要靠问人。** 问人还有一个副作用 ——
人会记错型号（本项目已经吃过一次"资料说 CO5300，实测是 SH8601"的亏）。

#### AXP2101：不用 XPowersLib，裸 I2C 只读

与 PocketOracle 同一结论，这里再钉一遍：

1. `XPowersLib::begin()` 会先读 `0x03` 校验 chip ID，**型号/版本对不上就整体返回 false**，
   而我们要的只是读几个状态位；
2. 库的 `isCharging()` 之类前面还多一道 `INTEN` 使能位的门，又多一个失效点。

裸 I2C 把两道门都绕开。**全文件只有三处写寄存器**（都按"先读 → 只改需要的位 → 回读"做）：

| 寄存器 | 动它的理由 |
|---|---|
| `0x30` ADC_CHANNEL_CTRL | 打开 bit0(电池电压)/bit2(VBUS 电压)。**不开这两路 `0x34`/`0x38` 恒读到 0** —— 看起来就像"电池 0mV、电量 0%"，是本步最容易踩的假故障 |
| `0x68` BAT_DET_CTRL | 打开 bit0 电池在位检测。不开 `STATUS1.bit3` 可能恒 0 → "插着电池也报没电池" |
| `0x49` INTSTS2 | PWR 键事件**读后必须写回清标记**，否则同一次按键会被反复读到 |
| `0x41` INTEN2 | 打开 4 个 PWRON 事件位（边沿位比"短按/长按"可靠，后者要 PMU 内部计时窗口配合） |

寄存器表（全部对着 XPowersLib 的 `XPOWERS_AXP2101_*` 定义核过，不是照抄某个博客）：

```
0x00 STATUS1 : bit5 VBUS 电压正常 / bit3 电池在位 / [4:0] 其余状态
0x01 STATUS2 : [6:5] 1=充电中 2=放电 0=待机 / bit3 == 0 且 VBUS好 => VBUS_IN / [2:0] 充电状态机
0x03 IC_TYPE : AXP2101 固定 0x4A
0x30 ADC_CTRL: bit0 电池电压 / bit1 TS脚 / bit2 VBUS电压
0x34-35      : vbat，高 5 位 + 低 8 位，单位 mV
0x38-39      : vbus，高 6 位 + 低 8 位，单位 mV
0xA4 SOC     : 电量 0..100（**只在电池在位时有意义**）
```

> ⚠️ **不要在 `-1`（未知）时兜底成 100%**。上游 M5 那条路在拿不到电量时会回落到
> 一个"看起来正常"的值，结果是**插着 USB 的裸板和电池真充满在屏上完全一样**，
> 排查时完全分不清。本步的做法是如实返回 `-1` → 屏上显示 `--%`。

#### ES8311：引脚、时钟系数、以及"别预分配整段 PCM"

引脚全部来自 PocketOracle（微雪官方 `Arduino-v3.3.5-v2` 的 `pin_config.h`，
那份代码在这块板上放网络电台实测通过）：

```
BCK=9  WS/LRCK=45  MCK=16  DOUT=8  DIN=10(麦克风，本步不用)   PA 功放使能=GPIO46（高有效）
```

I2S 用 **ESP-IDF 的新标准驱动**（`driver/i2s_std.h`，本机 core 3.3.7-cn 里确认存在），
不引 ESP32-audioI2S —— 本步只要"响一声"，多装一个库不值。
`I2S_STD_CLK_DEFAULT_CONFIG` 的 `mclk_multiple` 默认就是 256，
所以 `48000 × 256 = 12.288MHz` 正好对上 ES8311 coeff 表里 `12288000 / 48000` 那一行。

三个实现取舍：

1. **不预分配整段 PCM**。上游在 12kHz 下建了 3240 个 int16 的数组；本步跑 48kHz，
   照搬就是 12960 帧（立体声 52KB）。改成按 256 帧一块**流式生成 + 立即写 I2S**，
   一个 1KB 的静态块就够。
2. **ES8311 序列照搬 PocketOracle 的 `es8311.cpp` 48k/16bit 分支**，只把 DAC 音量单独设 `0xE0`
   （上游 M5 profile 用 `0xEF` 接近满；提示音本身峰值只有 0.135 满幅，留点余量压底噪）。
3. **播完按 `150ms` 尾音延时关功放**。`i2s_channel_write` 是"写进 DMA 就返回"，
   立刻拉低 PA 会把最后一段尾音切掉、还会"啪"一声。

#### 两个移植要点（都容易写错）

1. **完成提示音必须判"状态跃迁"，不能只看当前状态。**
   主机约 1 分钟轮询一次 `device.status`，一个一直停在 Complete 的 Agent
   会被反复当成"刚跑完"，提示音响个不停。判据必须是
   `上一次 != Complete && 这一次 == Complete`（上游 `detectAgentTransitions()` 的原逻辑）。
2. **`ble.setBattery()` 只在值变了的时候调。** 遥测函数每个 loop（5ms）跑一次，
   无条件上报等于往 BLE 里灌毫无意义的流量；而且 `-1`（没数据）时**根本不该上报**，
   否则主机会把它当成"0%"。

#### 新增串口命令

```
p         AXP2101 现场：0x00/0x01/0x30 原始值 + vbat/vbus/SOC + PWR 键事件位
e         ES8311 关键寄存器现场（0x00..0x37 共 18 个）
g         播放完成提示音（A4 -> C#5，270ms）
m         播放 880Hz 300ms 测试音（用来把"功放/喇叭不行"和"生成不对"分开）
w0 / w1   关 / 开功放 PA(GPIO46)
b <0..100> 临时覆盖电量显示；b -1 恢复 AXP2101 真值
g         模拟一次"A1 完成"（横幅 + 提示音），用来验证完成后的整段动作
```

#### 2026-09-24 首次烧录实测（编译 809518 B / 25%，globals 32156 B / 9%，无警告）

开机一次性把三个问题都答了：

```
[pmu] AXP2101 probe=40 id=0x4A(对) ADC 0x30=29->29 电池检测 0x68=1->1 INTEN2 255->255
[pmu] 首次读数 电量=100% 充电=0 VBUS=1 vbat=4153mV vbus=5028mV
[audio] ES8311 addr=0x18 ack=1 codec=1 i2s=1 @48000Hz bck=9 ws=45 mck=16 dout=8 pa=46
```

> ⚠️ **这三行的数字是十进制**（printf 用的是 `%d`，只有 `0x00/0x01` 那几行是 `%02X`）。
> `probe=40` 就是 `STATUS1 = 0x28`；`ADC 0x30=29->29` 是 `0x1D`。别当十六进制读，会得出
> "寄存器被改了"的错误结论。

**结论**：

| 问题 | 答案 |
|---|---|
| PMU 在总线上吗 | 在。`0x34` 有应答，`0x03 = 0x4A` = AXP2101 |
| 那三处使能写进去了吗 | **不用写** —— ADC 通道（`0x30=0x1D`，bit0/bit2 已开）、电池在位检测（`0x68=1`）、PWR 中断（`INTEN2=0xFF`）**出厂就是开的**。三处 `writeReg` 全部因为"值没变"而没发出去 ⇒ **本步对 PMU 是真正意义上的只读** |
| 有没有接电池 | **接了**。`STATUS1.bit3=1`、`vbat=4153mV`、`SOC(0xA4)=100`。`充电中=0` 是因为电池已经满了（4.15V），不是故障 |
| 有没有插 USB | 插了。`vbus=5028mV`，`VBUS好=1`、`VBUS_IN=1` |
| 编解码器认不认 | **认**。`0x18` ACK=1，配置序列全部落地（见下），I2S 也起来了 |
| PWR 键有事件吗 | `0x49=0x00` —— 没人按过（要按一下才知道这条线通不通） |

`e` 命令回读的 18 个寄存器与写下去的值**逐个吻合**：

```
0x00=80(power on) 0x01=3F(all clocks) 0x02=00(pre_div=1,1x) 0x03=10(fs_mode=0,adc_osr)
0x04=10(dac_osr)  0x05=00(adc/dac_div=1) 0x06=03(bclk_div=4) 0x07=00(lrck_h) 0x08=FF(lrck_l)
0x09=0C 0x0A=0C(16bit)  0x0D=01 0x0E=02 0x12=00(DAC上电) 0x13=10(HP输出)
```

**加入 I2S 之后的资源账**：`heap=216648` 恒定（step2/step4 是 225~227KB），

30 秒窗口内五次采样**零抖动**（无泄漏）。BLE 侧毫无影响：2.9s 连上、

### 8.22 PWR 键不在 AXP2101 的 PWRON 上：三条候选通道怎么一次问清（2026-09-24）

**症状**：老胡在板子前按了 PWR 键，串口**一行日志都没有**；`p` 打出来 `0x49=0x00`。

**第一层推理（把范围一刀切掉一半）**：AXP2101 的 `0x48/0x49/0x4A` 是**中断状态**寄存器，
`0x40/0x41/0x42` 是**中断使能**寄存器。使能位只决定 **IRQ 引脚输不输出**，
**不影响状态位本身的置位**。所以"`0x49` 一位都没置起来" ≠ "中断没使能"，
而是 **PWRON 这条线上真的没有电平变化**。使能位也别急着怀疑：开机日志里
`INTEN2 255->255`（补上 bit0/bit1 后是全 1，见下）已经是开着的。

**位定义的权威来源**：不要凭"看起来合理"自定义。查到的两处互相印证的一致结论是：

| 寄存器 | 位 | 含义 |
|---|---|---|
| `0x41` INTEN2 / `0x49` INTSTS2 | **bit0** | PWRON **正沿**（抬手） |
| 同上 | **bit1** | PWRON **负沿**（按下） |
| `0x48/0x49/0x4A` | 属性 | **RW1C**：读**不清**标记，写 1 才清 |

- 佐证 1：Zephyr 上游驱动 `drivers/mfd/mfd_axp2101.c` ——
  `AXP2101_IRQ_ENABLE_1_PWR_ON_NEG_EDGE_IRQ = BIT(1)`、`..._POS_EDGE_IRQ = BIT(0)`，
  并把 REG 0x41/0x49 直接称为 IRQ_ENABLE_1 / IRQ_STATUS_1。
- 佐证 2：AXP2101 数据手册寄存器表 —— `0x41` 默认 `0xfc`、`0x48~0x4A` 默认 `0x00` 且为 RW1C。
  ⇒ **PWRON 的两个边沿中断出厂是关的**（`0xfc` 的 bit0/bit1 = 0），要自己补上。

> 两条实测推论，直接改掉了旧代码里的两处错：
> 1. 注释里"0x49 由 pollPek **读**后清标记"是错的（读不清、写 1 才清）；
> 2. 只掩码 `0x0F` 打日志很危险 —— 万一真实位在 bit4~7，日志会**看起来像什么都没发生**。
>    所以 `p` 命令现在**原样**打印 `0x48/0x49/0x4A` 的整字节，掩码只用于解码。

**第二层：按键到底接在哪**。翻 1.8 的官方原理图（`files.waveshare.com/wiki/ESP32-S3-Touch-AMOLED-1.8/…pdf`）：
板上除 AXP2101 外还有 **U7 = TCA9554PWR**（原理图标题 "I/O Extensions"），
引脚名直接就是 `EXIO0..EXIO7`，挂在同一条 `ESP32_SDA/ESP32_SCL` 上，
地址由 A2A1A0 决定 ⇒ **0x20~0x27**。PocketOracle 里那条
"某些批次 PWR 键挂在扩展 IO 的 **EXIO4**（高有效）"的后备通道，说的就是它。

**做法（`x` 命令）**：与其猜，不如把三条候选通道同时挂上监听，让"按下这一下"自己指认：

| 通道 | 读什么 | 说明 |
|---|---|---|
| ① PMU | `0x48/0x49/0x4A` | RW1C，会一直留着，press 后立刻可见 |
| ② 扩展 IO | TCA9554 `0x00/0x01` | 逐位报 `EXIO0..7` 的跳变 |
| ③ 空闲 GPIO | `0,1,2,3,13,17,18,38,39,40,41,42,47` | 万一还有第三种走线 |

③ 的名单是**排除法**列出来的，碰不得的脚都在注释里写明理由（26~37 是闪存/八线 PSRAM、
19/20 是原生 USB、43/44 是控制台……）。名单里**故意留了 GPIO0(BOOT) 当对照组**：
按 BOOT 应该在 ③ 里看到 `G0:1->0`，看不见就说明"这个测法本身失效"，
而不是"信号不存在" —— 用对照组把**测法失效**和**真没信号**分开，比事后隔空争论省事。

> **窗口 vs 常驻**：④ 的触摸调试已经踩过一次"给了个时间窗口，窗口里没人点屏，
> 于是得到 900 秒零事件"的坑。所以嗅探**不设窗口、常驻监听**，
> 只在变化时打印 —— 老胡什么时候按都行，不需要配合时机。

**日志怎么读**（样例形状）：

```
[keys] 扩展 IO 扫描 0x20..0x27 应答: 0x20
[keys] 用 0x20: config(0x03)=0xFF(全输入) polar(0x02)=0x00 port0=0x?? port1=0x00 -> EXIO4=? （静止电平）
[x] +1830ms [扩展IO 0x20] port0=0x?? port1=0x00  EXIO4:0->1
[x] +2100ms [扩展IO 0x20] port0=0x?? port1=0x00  EXIO4:1->0
```

- 只有 ① 有变化 ⇒ PWR 在 PWRON 上，那要回头查 PMU 侧（`0x27` 按键时间/电平配置）。
- 只有 ② 有变化 ⇒ PWR 在扩展 IO 上，`BoardKeys` 就是正解，`BoardPower` 的 PEK 那条降级为备用。
- 只有 ③ 有变化 ⇒ 走的是普通 GPIO，按日志里的脚号去写第三套。
- 三条都不动、而 BOOT 对照组动了 ⇒ 这颗键**没被引到任何可读的地方**，只能当作纯电源键。


### 8.23 第一次三通道嗅探（240 秒）：唯一那条事件是"充电完成"，不是按键（2026-09-24）
240 秒常驻采集，全文只有 **1 条**事件（同一个 50ms 采样里打出两行）：

```
[keys] 扩展 IO 扫描 0x20..0x27 应答: 0x20
[keys] 用 0x20: config(0x03)=0xFF(全输入) polar(0x02)=0x00 port0=0xEF port1=0xFF
[i2c] 总线扫描: 0x15 0x18 0x20 0x34 0x51 0x6B   共 6 个
[  0.99] [x] 监听中（常驻）。基线：扩展IO port0=0xEF port1=0xEF | PMU 00/00/00 | GPIO=0010
[ 94.70] [x] +94057ms [扩展IO 0x20] port0=0xCF port1=0xCF  EXIO5:1->0
[ 94.70] [x] +94057ms [PMU] 0x48=0x00 0x49=0x00 0x4A=0x10
[ 99.97] [status] … bat=100 chg=0 …        ← 注意 94.96 那拍还是 chg=1
[154.72] [x] 监听中 +154s（已见 2 次跳变…）  ← 之后 145 秒 EXIO5 一直保持低，没有"抬起"
```

#### 关键修正：`0x4A bit4` 是 **BAT_CHG_DONE**，不是按键

`0x4A=0x10` 看着像"某位按键事件"，实际是 **INTSTS3 bit4 = 电池充电完成**。
位定义（`XPowersLib/src/XPowersParams.hpp` → `xpowers_axp2101_irq_t`，使能寄存器
`0x40/0x41/0x42` 的低 8 位一一对应状态寄存器 `0x48/0x49/0x4A`）：

| 状态寄存器 | bit0 | bit1 | bit2 | bit3 | bit4 | bit5 | bit6 | bit7 |
|---|---|---|---|---|---|---|---|---|
| `0x48` | BAT_UT | BAT_OT | CHG_UT | CHG_OT | SOC_NEW | WDT_TO | SOC_WL1 | SOC_WL2 |
| `0x49` | **PWR_POS** | **PWR_NEG** | PWR_LONG | **PWR_SHORT** | BAT_OUT | BAT_IN | VBUS_OUT | VBUS_IN |
| `0x4A` | BAT_OVP | CHG_TIMER | DIE_OT | CHG_START | **CHG_DONE** | BATFET_OCP | LDO_OCP | WDT_EXP |

三份证据互锁，说明 94.7 秒那一下是**电池充饱**：

1. `0x4A` bit4 = CHG_DONE 置位；
2. 同一采样 `chg` 仍在 1，5 秒后（99.97s）变 0 —— 充电状态机退出充电；
3. 扩展 IO 的 **EXIO5 从 1 掉到 0 之后 145 秒都没回到 1** ——
   **真人按一下必然有"按下→抬起"两个沿**，只有状态类信号才会"掉下去就不动"。

⇒ **EXIO5 不是按键**（按一下必然有"按下→抬起"两个沿，只有状态类信号才会"掉下去就不动"）。
但它**也不是"充电指示灯"** —— 复位后（`chg=0`、`0x4A=0x00`）再读，**EXIO5 又变回 1** 了。
把两条合起来看，最自洽的解释是：

> **EXIO5 ≈ AXP2101 的 `AXP_IRQ` 中断输出线**（开漏、低有效、**锁存到中断状态被清掉为止**）。
> - 94.7s 那一下 `0x4A` 置了 CHG_DONE ⇒ IRQ 线拉低 ⇒ `EXIO5:1->0`；
> - 我们的固件只清 `0x49`、从不写 `0x4A` ⇒ 位一直留着 ⇒ **IRQ 线保持低 145 秒不抬**；
> - 复位后 `0x4A=0x00`（状态被清）⇒ **IRQ 线释放 ⇒ `EXIO5` 回 1**。三个现象一条线解释完。
>
> 若成立，这是个**好消息**：PMU 的中断在扩展 IO 上**读得到**，PWR 键可以做成
> "扩展 IO 中断驱动"而不是纯轮询。⚠️ 但这条**目前是假设**，需要"按一次 PWR 应该有
> `EXIO5` 下降沿 + `[pmu] PWR 键事件`（两条同时出现）"来验。
>
> 而 PocketOracle 点名的 **EXIO4 全程恒为 0**（静止即 0，"按下变高"与它不矛盾）——
> 到底是不是 PWR 键，这一轮**没有拿到任何证据**，因为这一轮
> **根本没抓到一次真实按键**（含 BOOT 对照组：`G0` 一次都没跳过）。

> **教训（比结论更重要）**：`0x4A` 和 `0x49` 只差一个寄存器号，位序也看着相似，
> 把 `0x4A bit4` 读成"按键相关"会得到一个**自洽但完全错误**的故事
> （"按到了某个键"）。所以日志里现在**直接打位名**（`0x4A:CHG_DONE`），
> 而不是只打十六进制 —— 只打十六进制时，每次都要回头查表，而查表恰好是最容易出错的一步。

#### 顺带发现的一个"仪器坏了"：`0x49` 那一格永远是 0

`loop()` 里的顺序是 `pollPowerButton(); pollPwrMonitor();`。前者的
`pollPek()` 读 `0x49` 之后**会把位写回清零**（RW1C），所以等轮到嗅探去读时，
`0x49` 早就被清干了 —— **嗅探的 PMU 通道对 PWRON 是瞎的**，不是"没信号"。
PEK 事件其实由 `[pmu] PWR 键事件 …` 那条线报出来，两条线不能混着看。

⇒ 现在 `pollPowerButton()` 的事件也会进事件环，两条线合并到一处。

#### 做法升级：事件环（把"时机"彻底从排查里拿掉）

"常驻实时打印"只解决了一半问题 —— 另一半是**没人在抓串口时，那行日志就永远丢了**
（这一轮很可能就是这样：采集窗口 240 秒跑完，老胡才看到消息）。

所以加了 24 格事件环 `evtLog[]`：每条事件既实时打印、又进环，
新命令 **`xl`** 把开机以来的历史整条倒出来，并附一张**当场电平**快照：

```
[x] 事件历史 3/24 条（最早的在前，相对于开机）
[x]  #1 [x] +94057ms [PMU] 0x48=0x00 0x49=0x00 0x4A=0x10  0x4A:CHG_DONE
[x]  #2 …
[x] 当场 扩展IO 0x20 config=0xFF(全输入) port1=0xCF: EXIO0=1 … EXIO4=0 EXIO5=0 …
[x] 当场 PMU 0x48=0x00 0x49=0x00 0x4A=0x10  0x4A:CHG_DONE
[x] 当场 GPIO(电平，1=高): G0=1 G1=1 …
```

要点：
- **历史 + 当场电平必须一起看**：只有历史分不清"按完又抬起"和"一直压着"；
  只有当场电平分不清"从没动过"和"动过又回来了"。
- 心跳（60 秒一次）**只打串口、不进环** —— 否则长跑时心跳会把真正的按键事件挤出去。
  心跳里也带当场电平，用来区分"在听但信号没动"和"根本没在听"。
- 有了这个环，**按键再也不需要配合时机**：老胡随便什么时候按，之后任意时刻抓一段
  串口敲 `xl` 就能回看。

编译 815466 B(25%) / 全局变量 35084 B(10%)（事件环 24×120B ≈ +2.9KB），无警告。
烧录后实测（`tools/tap_send.py COM11 7 "xl" 8`）：

```

[x] 当场 PMU 0x48=0x00 0x49=0x00 0x4A=0x00
```

### 8.24 PWR 键定位完成：**双通道**（2026-09-24）

老胡按了一轮（BOOT + PWR 各若干次，板子**没有黑屏/关机/重启**），
用 **不复位**的方式读事件环（`tools/tap_peek.py`），拿到开机以来 24 条完整事件：

```
[x] 事件历史 24/24 条（最早的在前，相对于开机）
 #1 [pmu] PWR 键事件 0x02 PRESS(负沿)        0x49:PWR_NEG
 #2 [x] +534367ms [扩展IO 0x20] port0=0xFF   EXIO4:0->1     ← 按下
 #3 [pmu] PWR 键事件 0x09 RELEASE(正沿) SHORT  0x49:PWR_POS 0x49:PWR_SHORT
 #4 [x] +534524ms [扩展IO 0x20] port0=0xEF   EXIO4:1->0     ← 抬起（157ms 后）
 …
 #13 [x] +552280ms [GPIO] G0:1->0      ← BOOT 按下（对照组）
 #14 [x] +552438ms [GPIO] G0:0->1      ← BOOT 抬起
```

#### 三条结论

1. **PWR 键是"双通道"，不是"二选一"** —— 同一颗键被引到了两处，两条线**每次都同步响应**：
   | 通道 | 按下 | 抬起 |
   |---|---|---|
   | AXP2101 `0x49` | `0x02` = PWR_NEG（负沿） | `0x09` = PWR_POS \| PWR_SHORT |
   | TCA9554 `0x20` bit4 | EXIO4 `0->1` | EXIO4 `1->0` |
   ⇒ PocketOracle 里那条「PWR 可能挂在 EXIO4」的注释**是真的**，而它同时也在 PWRON 上。
   ⇒ **EXIO4 是高有效（按下 = 1）**，静止 = 0。
2. **BOOT 键 = GPIO0，低有效**（`G0:1->0` 按下 / `0->1` 抬起）。它的意义不只是"多一个键"——
   它是**对照组**：它跳变了，就证明整套嗅探方法本身有效，于是"PWR 两条通道也都跳了"才是可信的。
3. **一次短按 = 两条 PMU 事件**：按下那条只有负沿（`0x02`），抬手那条才有 `SHORT`（`0x09`）。
   ⇒ 拿 `SHORT` 当"点击"动作**天然只会触发一次**，不必额外去重。

#### 对 §8.23 那个假设的更新：EXIO5 = AXP_IRQ（更自洽了，但**不能拿它做按键检测**）

§8.23 猜「EXIO5 ≈ AXP2101 的 `AXP_IRQ` 中断输出线（低有效、锁存到状态被清）」。这一轮：
**PWR 按下时 EXIO5 一动没动**（整段 560 秒恒为 1）。这不否证假设，反而对得上——
`pollPek()` 每 50ms 就把 `0x49` 清掉，IRQ 线只低 ≤50ms，而嗅探每 30ms 采一次，**可能整段错过**；
而 CHG_DONE 那次能保持低 145 秒，正因为我们**从不写 `0x4A`**。

但结论要收紧：**不要靠 EXIO5 做"按键中断驱动"** —— 它的低电平窗口短到抓不住。
要检测按键就老老实实读 `0x49`（PMU 通道）或 `0x20` 的 bit4（扩展 IO 通道）。

#### 落地：物理按键照上游定义接上（`_src/src__main.cpp` updateBoardButtons()）

| 键 | 通道 | 动作 | HID 报文 |
|---|---|---|---|
| BOOT | GPIO0，低有效，**40ms 消抖**，电平触发 | 按住说话（Push to talk） | `ACT10` 按下 … 抬起 |
| PWR | AXP2101 PEK，50ms 轮询 | 短按 = 语音聊天开关 | `ACT09` 按下 →**70ms**→ 抬起 |
| PWR | AXP2101 PEK | 长按 | **软件不接管**：AXP2101 硬件约 6s 自己关机 |

- `pttDown` 一个状态位管住"已发按下、未发抬起"，真按键和模拟共用，**不会重复发**。
  消抖沿用上游写法："电平变了、且已稳定超过 40ms 才算数"。
- `beginVoiceChatClick()` 照上游：先补上一次没收尾的抬手，再发按下，70ms 后收尾 ——
  连按两次也不会让主机看到"两次按下中间没有抬起"。
- 新命令 **`n`**（模拟按住说话，150ms 后自动抬）/**`y`**（模拟 PWR 短按）——
  走的是和真按键**同一条代码路径**（`pttPress()` / `beginVoiceChatClick()`），
  所以验的是真实行为、不是旁路。
  ⚠️ 本来想用 `t`，但 `t` 已经是"屏自检"了；`v`/`w` 与 `v0/v1`/`w0/w1` 易混，所以选了 `n`/`y`。

#### 落地实测（编译 816538 B / 25%，globals 35108 B / 10%，无警告）

```
>>> SENT: n
HID key=ACT10 action=1
[btn] PTT 按下 -> ACT10 1
HID key=ACT10 action=0          ← 160ms 后（kSimPttHoldMs=150 + loop 的 5ms）
[btn] PTT 抬起 -> ACT10 0

>>> SENT: y
HID key=ACT09 action=1
[btn] 语音聊天 -> ACT09 一颗 70ms 脉冲
HID key=ACT09 action=0          ← 80ms 后
```

两条路径都通。真按键（BOOT / PWR）走的是**同一批函数**（`pttPress` / `beginVoiceChatClick`），
所以剩下的只是"电平/中断有没有进到 poll"这一步。

`[status]` 新增三位：`ptt=`（已发 ACT10 按下未抬起）/`boot=`（BOOT 脚消抖后电平）/
`vc=`（ACT09 脉冲待收尾）。

#### 这三个坑都值得记（全部在 2026-09-24 这一轮踩到）

1. **Edit 报 success 但没落盘 —— 单独发的也会丢**。`n`/`y` 的命令分发分支
   和 loop 里的三个函数调用，回报全是 success，实际一行没写进去。
   发现方式是"编译过了、烧进去却回 `[cmd] unknown: n`"。
   ⇒ **这两类改动编译器抓不到**：① 新增命令分支；② 新增函数调用。
   **改完立刻 Grep 复核，再编译。**
2. **只给函数加前置声明、忘了变量** ⇒ `error: 'pttAutoReleaseAtMs' was not declared in this scope`。
   函数有原型可以先声明，**变量没有原型** ⇒ 定义必须物理上位于使用点之前
   （或写 `extern`）。现在 6 个按键状态变量都定义在文件前部。
3. **编译失败时 `upload rc=0` 照样"成功"** —— build 目录里还留着**上一次的 .bin**，
   烧进去的是旧固件，现象和"代码没改"一模一样。
   ⇒ 编译和烧录必须用 `if [ $RC -eq 0 ]` 串起来；只看 upload 的成功回执会被骗。



#### 方法论（三条，比结论更可复用）

1. **读历史必须"不复位"地打开串口**。ESP32-S3 原生 USB 在 RTS=1 时会拉低 EN 复位，
   于是 RAM 里的事件环被清空、`xl` 打出"0 条"——**看起来像"按键没反应"，其实是证据被自己擦掉了**。
   `tools/tap_peek.py` 用 `dtr=0/rts=0` 打开，专门用来读"上一次开机以来的痕迹"。
2. **给窗口就不再依赖人的时机**。§8.23 那次 240 秒采集"白跑"，根因是采集跑完老胡才看到消息。
   事件环 + `xl` 之后，按键**什么时候按都行**，按完再读 —— 这一轮一次就成功。
3. **先证明"仪器在听"，再解释"为什么没信号"**。BOOT 对照组（GPIO0）是廉价的自我校验：
   它不动 ⇒ 怀疑仪器；它动了 ⇒ 没动的那些通道才是真的没接。

### 8.25 真按键实测翻车：`ACT09` 的真身是「新开分支」，不是语音聊天

老胡短按 PWR 后，ChatGPT 桌面端执行的是 **"Continue the current chat in a new chat"（新开分支）**。
固件侧完全正确（`y` 与真按键都打出 `HID key=ACT09 action=1 … 0`），
**问题不在固件、不在 BLE、不在按键通道，在桌面端的键位配置。**

#### 根因：`ACT09` 是「第 4 个 Command Key」，而出厂默认动作就是新开分支

官方文档 (learn.chatgpt.com/docs/features/codex-micro) 写明 Codex Micro **默认布局六个动作**：

| 官方控件 | 出厂默认动作 | 对应上报键名 | 状态 |
|---|---|---|---|
| Command Key 1 | Toggle Fast mode | `ACT06`? | **未验证**（推测） |
| Command Key 2 | Approve the current request | `ACT07`? | **未验证**（推测） |
| Command Key 3 | Decline the current request | `ACT08`? | **未验证**（推测） |
| **Command Key 4** | **Continue the current chat in a new chat** | **`ACT09`** | ✅ **实测确认**（老胡按 PWR = 新开分支） |
| Mic 开关 1（宽 Mic 键上半） | Push to talk | `ACT10` | ✅ 实测（按住说话） |
| Mic 开关 2（宽 Mic 键下半） | —（默认合并成一个 Mic 键） | `ACT11` | 未验证 |
| Codex 键 | Send the message in the composer | `ACT12` | 上游已用 |
| 6 个 Agent Key | 跟随最近 6 个会话 | `AG00`..`AG05` | 上游已用 |

⇒ **`_src/src__main.cpp` 第 96-98 行那句注释是"作者的意图"，不是"出厂事实"：**

```cpp
// ChatGPT 26.727 exposes one combined Mic key but no independent ACT10/ACT11
// switch setting. Use the fourth configurable Command Key for Voice Chat.
constexpr char kVoiceChatCommandKey[] = "ACT09";   // ← 上游只是"打算"这么用，没有真去桌面端改配置
```

他把第 4 个命令键**当作**语音聊天开关来发，但桌面端第 4 命令键的出厂动作是"新开分支"，
**上游从没在任何文档里写"要去设置里把它改掉"** —— README 那张表头写的是「**建议配置**」，
也就是说上游本来就假定用户自己去桌面端配。老胡这边没人配过 ⇒ 走的就是出厂默认 ⇒ 新开分支。

#### 官方给的两条正路（都不需要改固件接线，只有 B 需要改一行键名）

- **路线 A（首选，零固件改动）**：ChatGPT 桌面端 → **设置 → Codex Micro** →
  在「Design 预览」里点 Command Key 4 → 把动作改成 `Push to talk` / `Voice chat`。
  官方说重新分配后**建议把物理键帽也换掉**；`Restablecer diseño`（重置布局）会恢复出厂。
- **路线 B（更贴合两颗物理键，推荐）**：官方文档提到 **"Use separate mic keys"（分离麦克键）** ——
  那个**宽 Mic 键底下其实是两个开关，可以分别分配**。
  打开它之后把「第二个 Mic 开关」设成 **Voice chat**，固件把 `kVoiceChatKey` 从 `ACT09` 改成 `ACT11`。
  这样 BOOT = `ACT10` 按住说话、PWR = `ACT11` 语音聊天，**和上游注释里"独立 ACT10/ACT11"的说法终于对上**。
  ⚠️ 上游看到的 26.727 还没有这个选项，官方文档是新版措辞 ⇒ **这依赖老胡本机桌面端版本，先去设置页看有没有这个开关**。
- **路线 C（兜底）**：伴进程 `_src/companion-win/src/codex_watch_all.py` 里，
  `ACT09` 是它**自己**用 bleak 截获后触发 `Ctrl+Shift+D`（`trigger_codex_voice()`）实现的语音聊天，
  完全绕开桌面端设置。代价是必须常驻跑 Python 伴进程。

#### 关键认知（比这次的具体结论更值钱）

1. **键名只是"插槽编号"，功能由桌面端「设置 > Codex Micro」决定**。
   设备端说 `ACT09` 只是说"第 4 号命令键被按了"，它**无权决定**这个键干什么。
   ⇒ 以后遇到"按键行为不对"，先分清楚是**设备没发**还是**桌面端没绑对**——
   看串口有没有 `HID key=... action=...` 就能一刀切开。
2. **上游代码注释里的"对齐说明"要当"待验证假设"读**，别当规格。
   上一轮 PWR 双通道（§8.23/8.24）是老胡实测证实的，这一轮 `ACT09` 则是实测**推翻**了注释。
3. **不用改固件就能枚举键名**：固件已有 `k <KEY> [act] [agent]` 命令，
   直接 `k ACT11 1` / `k ACT11 0` 就能试任何键名在桌面端的反应，不必重新编译烧录。

直接 `WebFetch` `learn.chatgpt.com/docs/features/codex-micro` 会被拒（`fetch failed`，
该域名对无头客户端不友好），但**搜索能拿到正文**，且**中文镜像 `codex-docs.com/docs/features/codex-micro`
的措辞与官方原文一致**。原文两段：

默认布局（六个动作）：

⇒ **"使用独立麦克风按键"确实是官方功能** ⇒ §8.25 的**路线 B 成立**；
且"语音聊天"是**麦克风键的下拉选项之一** ⇒ **路线 A 也成立**。
两条路都指向同一个动作：**去桌面端配**，固件侧本来就只是"发编号"。

#### 8.25.2 固件落地：PWR 键目标键名改成"运行时可改"，默认避让 `ACT09`

既然"哪个开关对应哪个 ACT 编号"**只能实测**，就不该把键名写死。
改动全在 `firmware/step5_power_audio/step5_power_audio.ino`：

| 项 | 改前 | 改后 |
|---|---|---|
| 键名载体 | `constexpr char kVoiceChatKey[] = "ACT09"` | `char gVoiceChatKey[8] = "ACT11"`（变量，运行时可改） |
| 默认值 | `ACT09`（出厂动作 = 新开分支，**误触即刻分叉对话**） | `ACT11`（若无人认领则无副作用，比误开分支安全得多） |
| 运行时换绑 | — | 新命令 **`vc [ACTxx]`**：`vc` 看当前值、`vc ACT11` 就地改，**零重编译** |
| 事件环文案 | 写死 `"[btn] 语音聊天 -> ACT09 …"` | `snprintf(..., "%s", gVoiceChatKey)`，跟着实际键名走 |
| `printStatus` | `ptt=/boot=/vc=` 三个 `%d` **没传实参**（打出来是栈垃圾） | 补上实参 + 新增 `vck=<当前键名>` |

顺带修掉一个真 bug（§8.21 那条"参数与占位符必须一起改"的**复发**）：
`printStatus` 的 `ptt=%d boot=%d vc=%d` 三个占位符一直没有对应实参 ——
变参函数"占位符多于实参"是**未定义行为**（读栈垃圾），而 `Serial.printf` 这条路
**不做 `-Wformat` 检查 ⇒ 零警告**，所以只能靠人复核。
（上一轮加 `ptt/boot/vc` 时只改了格式串、忘改参数，正好又撞上同一个坑。）

**结论**：真按键发的键名从此可以现场 A/B —— 在桌面端把某个开关设成"语音聊天"后，
敲 `vc ACT11`（或 `ACT10`）再按一下 PWR，看 ChatGPT 的反应即可定案，全程不动编译器。

#### 8.25.3 最终结果：`ACT11` 就是"第二个麦克风开关"（2026-09-24 打通 ✅）

老胡在桌面端打开「使用独立麦克风按键」、给**第二个开关选上「语音聊天」**之后，
短按 PWR **生效**。事件环对账（`xl`）：最近 4 次 PWR 短按全是完整一颗脉冲，
`vck=ACT11`（**没改过编号**，用的就是固件默认值）：

```
#5  0x02 PRESS(负沿)  0x49:PWR_NEG
#6  +1836330ms [扩展IO 0x20] port0=0xFF  EXIO4:0->1
#7  0x09 RELEASE(正沿) SHORT
#8  [btn] 语音聊天 -> ACT11 一颗 70ms 脉冲
```

⇒ **宽麦克风键拆出的两个开关：第一个 = `ACT10`（按住说话）、第二个 = `ACT11`（语音聊天）**，
和上游注释里那句 "independent ACT10/ACT11" 的猜测终于对上
（只是上游手上那版桌面端还没有这个开关）。固件默认值 `ACT11` 猜对了，`vc` 这次没用上 ——
但它就是为"猜错"准备的保险，留着。

**老胡第一次报"没反应"时的诊断路径（可复用）**：不猜、不重烧，**先读事件环** →
设备侧一条不少（`PRESS` / `EXIO4` / `RELEASE` / 脉冲全在）⇒ 直接判定"桌面端没绑"，
再问一句"设置页做到了哪一步"，即定位到"**打开了开关但没选动作**"。

> **「按键不对」类问题的通用切分法**：
> `xl` **有**记录 = 桌面端的问题；`xl` **没有**记录 = 设备侧的问题。
> 外加一条易漏的认知：打开「独立麦克风按键」只是把宽键**拆成两个开关**，
> **每个开关还要各自去下拉里选动作**，空着 = 没绑。




### 8.26 step6：配额伴进程（Windows BLE）—— 把 Codex 剩余额度推到板子（2026-09-24 打通 ✅）

**产出**：`companion/codex_quota_bridge.py`（+ `companion/run_quota_bridge.bat` 启动器）。

#### 链路（每轮）

```
读 %CODEX_HOME%/auth.json 的 tokens.access_token
  → GET https://chatgpt.com/backend-api/wham/usage
  → 取 rate_limit.primary_window.{used_percent, reset_after_seconds}
  → 换算 {"remaining_percent": <float>, "reset_in_seconds": <int>}
  → BLE 连板子，写 GATT 7f0d4e66-…-5c02
  → **写完立即断开**（链路还给 HID 驱动）
  → 等 interval 秒（默认 120），再来一轮
```

#### 与上游 `codex_watch_all.py` 的取舍：只留一半

上游那个 all-in-one 干两件事，第二件对我们是**死代码**：

| 上游功能 | 我们 | 理由 |
|---|---|---|
| ① 配额同步（auth.json → wham/usage → 私有 GATT） | ✅ 原样保留 | 这是 ⑥ 的全部意义 |
| ② 按键桥接（订阅 HID input `0x2A4D` → 自己发 `Ctrl+Shift+D` / Enter） | ❌ 整块砍掉 | 它订阅的是上游 1.75C 额外暴露的 vendor control service `5f9d4e66-…-5c11`，**我们固件里没有这个服务**（grep 确认）；而且真 `0x1812` 被 Windows 隐藏、ChatGPT 原生读 report，上游注释自己也承认这条桥"不再用得上" |

顺带把 **`codex app-server` 子进程依赖也砍了** —— 上游为 turn/joystick 启它，我们只读配额，
纯 HTTP + auth.json ⇒ **不需要 codex CLI 在 PATH 上**，更不需要 `ctypes` 键盘模拟。
结果：约 570 行 → 不到 300 行，无 subprocess、无 SendInput、无额外依赖（只要已经装好的 bleak）。

#### 硬契约（对着固件 `CodexMicroBle.cpp` / `QuotaPayload.h` 抄的，改这里 == 改协议）

| 项 | 值 | 备注 |
|---|---|---|
| 广播名 | `Codex Micro` | 固件 `kDeviceName[]`，与上游扫描名一致 |
| 服务 UUID | `7f0d4e66-2ac2-4a71-bfbe-4ef61a0e5c01` | 私有，不是标准 GATT |
| 写特征 UUID | `7f0d4e66-2ac2-4a71-bfbe-4ef61a0e5c02` | `ESP_GATT_PERM_WRITE` |
| payload | `{"remaining_percent":<float>,"reset_in_seconds":<int>}` | 固件 `onQuotaWrite()` 限长 **512B** |
| 成功日志 | 串口 `Quota update remaining=%.1f reset=%lus` | 失败则是 `Quota update rejected: invalid fields` |

#### 三个坑（都在 2026-09-24 这一轮踩到 / 提前避开）

1. **`remaining_percent` 必须是 float，不能是整数。**
   固件 `quota_payload::parse()` 第一句就是 `remaining.is<float>()`；整数 JSON 在部分
   ArduinoJson 版本下过不了，会被判 `invalid fields`。
   ⇒ 伴进程里显式 `round(100.0 - used_f, 1)`，序列化出来一定带小数点（实测发的是 `100.0`）。
   **上游发的正是整数**（`int(round(100 - used_f))`），照抄就会踩 —— 这是"移植要核对契约、
   不能只抄代码"的又一例。

2. **写完必须立即断开。** Windows 基本只维持**一条** LE 连接，伴进程占着连接时
   ChatGPT 的 HID 会话会被挤掉（按住说话 / 语音聊天失灵）。
   `async with BleakClient(...)` 里写完就退出 ⇒ 自动断开。
   **实测**：断开后 ChatGPT **自己就重连回来了** —— 紧跟着读 `s` 仍是 `connected=1 peers=1 rpc=1`，
   所以"周期性抢一下链路"的代价只有连接那一两秒。

3. **代理：终端注入的 `HTTP(S)_PROXY` 未必放行 chatgpt.com。**
   本机诊断（`build/diag_proxy.py`）显示**两个代理打架**：

   | 来源 | 值 | 结果 |
   |---|---|---|
   | 沙箱/终端注入的环境变量 | `127.0.0.1:41768` | ❌ `Tunnel connection failed: 502`（它把外网请求挡了） |
   | 系统注册表 `ProxyServer` | `127.0.0.1:10808` | ✅ 真能出去的是这个 |

   ⇒ 脚本加了 `--proxy URL` 显式覆盖。**在你自己（非沙箱）的 PowerShell 里跑时不用带**，
   urllib 会读注册表自动走 10808；只有环境变量里有"假代理"时才需要。

#### 本机实测证据（2026-09-24）

```
# ① 只读配额，不碰 BLE
$ py companion/codex_quota_bridge.py --dry-run --once --verbose --proxy http://127.0.0.1:10808
[19:06:27] quota remaining=100.0% reset_in=17568s

# ② 连板子写一次
[19:06:44] [ble] found Codex Micro [90:70:69:FE:97:A9]
[19:06:45] [ble] wrote {"remaining_percent":100.0,"reset_in_seconds":17551}
[19:06:45] [ble] disconnected
[19:06:45] pushed to watch

# ③ 设备侧自证（不复位读串口，quota 是 RAM 里的持久状态，不受时机影响）
[status] connected=1 peers=1 adv=1 rpc=1 quota=yes rem=100.0 … ptt=0 boot=0 vc=0 vck=ACT11

# ④ 连跑 3 轮，重复 connect/write/disconnect 稳定
[19:07:21] quota remaining=100.0% reset_in=17513s … pushed to watch
[19:07:25] quota remaining=100.0% reset_in=17510s … pushed to watch
[19:07:29] quota remaining=100.0% reset_in=17506s … pushed to watch
```

`reset_in_seconds` 逐轮递减（17513 → 17510 → 17506）⇒ 每轮读的都是**新**数据，不是缓存。
BLE 地址实测稳定为 `90:70:69:FE:97:A9`（Espressif OUI，芯片固定地址），
⇒ 可以 `--address 90:70:69:FE:97:A9` 跳过扫描（更快、更稳）。


**排障对照**：

| 现象 | 含义 |
|---|---|
| `no auth.json … run: codex login` | 没登录过 Codex CLI ⇒ 先 `codex login` |
| `HTTP 401/403` | token 过期 ⇒ 跑一次 Codex CLI（或开一下桌面端）刷新 `auth.json` |
| `Tunnel connection failed: 502` | 环境变量里有假代理 ⇒ 加 `--proxy http://127.0.0.1:10808` |
| `'Codex Micro' not advertising` | 板子没开机 / 没广播 / 被别的 LE 连接占着 |
| 串口 `Quota update rejected: invalid fields` | payload 字段类型不对（回到坑 1：必须带小数点） |

> **这条链路的观测法值得记**：配额**不进事件环**，但 `state_.quota` 是 **RAM 里的持久状态**
> ⇒ 推送之后随时敲 `s` 都能看到 `quota=yes rem=…`，**完全不用卡时机**。
> 和 §8.24 的 `xl` 是同一个思路：把观测点放在"结果状态"上，而不是"瞬时事件"上。
